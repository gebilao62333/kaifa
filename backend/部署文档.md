- **v6.19 变更**: 配合安全扫描 M-9（Nginx 安全响应头被 `location` 覆盖）。本轮**不新增任何环境变量、无库表变更、无迁移、无需重建 Redis、无需改 `docker-compose.yml`**，但**必须重新加载 nginx**才能让安全头在全站生效。运维侧必读四条：①**根因**——nginx 的 `add_header` **不合并继承**：任一 `server`/`location` 只要自带一条 `add_header`，就丢弃从上层继承的**全部** `add_header`。`nginx/nginx.conf` 的 `http` 块声明了 `X-Content-Type-Options`/`X-Frame-Options`/`Referrer-Policy`/`Content-Security-Policy` 四条基线，但 `nginx/conf.d/default.conf` 与 `nginx/conf.d/default.ssl.conf` 里的 `location /uploads/`（自带 `Cache-Control`）和 `location /admin`（自带 `Cache-Control`/`Pragma`/`Expires`）各自声明了 `add_header`——于是 `/uploads/*` 与 `/admin*` 的响应里这四条安全头**全部丢失**；443 站点的 `server` 块另自声明 HSTS 等，又丢弃了 `http` 层的 `Referrer-Policy` 与 CSP。②**修复**——新增片段文件 `nginx/conf.d/security-headers.inc`（通用四头，文件名用 `.inc` 以免被 `include conf.d/*.conf` `add_header` 的 `location` 在各自块内**重新 `include`** 对应片段，使安全头与 `Cache-Control` 并存；`X-Frame-Options` 全站统一为 `SAMEORIGIN`（原 443 写 `DENY`，与 CSP 的 `frame-ancestors 'self'` 不一致，且 `DENY` 会连本站同源嵌框一起禁掉）。③⚠️ **部署动作**：片段是新增文件，存在于 `nginx/conf.d/` 内、而该目录在 `docker-compose.yml` 已整目录只读挂载（`./nginx/conf.d:/etc/nginx/conf.d:ro`），**无需改编排**；升级后执行 `docker compose restart nginx`（或 `docker compose exec nginx nginx -s reload`）即可生效。**验收**：`curl -sI https://<域名>/admin/ | grep -iE "x-content-type-options|x-frame-options|referrer-policy|content-security-policy|strict-transport-security"` 应能看到全部头（修复前 `/admin/`、`/uploads/` 只剩 `Cache-Control`）；`curl -sI http://<域名>/uploads/<任一文件>` 应带四条通用头。④**行为变更**：`/uploads/` 与 `/admin` 的响应补齐安全头（443 下也补 HSTS）；443 的 `X-Frame-Options` 由 `DENY` 变 `SAMEORIGIN`（同源页面嵌框由「被禁」变「允许」，如无嵌框需求影响为零）。**遗留（如实标注，未伪造）**：①`add_header_inherit merge`（nginx 1.29.3+ 才支持，本仓库镜像 `nginx:1.26-alpine`）不可用，一致性依靠「片段在每个 `add_header` 块重复引入」维持——新增带 `add_header` 的 `location` - **v6.6 变更**: 配合安全扫描 H-4（令牌用途绑定 `type` 声明）。⚠️ **上线即失效全部既有登录会话**：升级前签发的 JWT 不带 `type`，新代码的 `authMiddleware`/`adminAuth`/Socket 握手都按用途白名单校验，一律判为无效 → C 端用户与管理端管理员都会被登出并跳转到登录页（前端 401/403 分支自动清本地登录态，无需人工干预，但**请安排低峰窗口发布并提前公告**）。①本轮**不新增任何环境变量**，`JWT_SECRET` 保持不变即可（换密钥同样会登出所有人，无需为此额外操作）；②`JWT_ALGORITHM=HS256` 一行经核对是**文档虚构键**——全仓库代码从不读取它（`config/jwt.js` 直接用 `jsonwebtoken` 默认 HS256），已在 4.1 标注删除以免误导运维排障；③`JWT_EXPIRES_IN` 默认 `7d` 偏长的口径记入遗留（本轮未改默认值，属运维策略：缩短会立刻放大「重新登录」频率，建议先做 H-5 服务端登出/吊销再评估）；④用途分工：`access`（业务接口 + Socket 握手，`JWT_EXPIRES_IN`）、`refresh`（仅 `/api/user/refresh-token`，`JWT_REFRESH_EXPIRES_IN`）、`admin`（仅 `adminAuth`）、`admin_refresh`（目前签发但无消费入口，遗留）。
- **v6.5 变更**: 配合安全扫描 H-3（后台登录防爆破）在 4.1「安全配置」段补四个可调环境变量并加排障说明——`ADMIN_LOGIN_RATE_LIMIT_MAX=5`（单 IP 15 分钟，**开发环境不豁免**）、`ADMIN_LOGIN_MAX_FAILS=5`（单账号 15 分钟窗口内失败即锁 15 分钟）、`LOGIN_RATE_LIMIT_MAX=20`（用户端，此前只能改代码）、`ADMIN_EMERGENCY_LOGIN=false`（应急账号开关）。⚠️ 关键运维含义：后台登录锁定状态存在 Redis（键 `admin:login:fail:<归一化账号>`），`adminLoginGuard` 在 Redis 不可用/命令报错/读写超 2 秒时**保守拒绝**并返回 503，因此「管理员登不进后台」先查 Redis 连通性；Redis 实例重建或清空会解除已生效的锁定，需要长期留证须另加审计存储（本轮遗留）。

```bash
# 验证码发送限流（60 秒窗口内允许的次数），默认 1
SMS_RATE_LIMIT_MAX=1
# 反向代理信任层级：决定 req.ip 取谁，也就是限流按谁计数。
# 默认 loopback（只信任同机反代，配 nginx 的 $proxy_add_x_forwarded_for 即可拿到真实客户端 IP）。
# 取值非法（true / * / all / 0.0.0.0/0 / 跳数>10 / 跳数与网段混写 / 主机位非零网段）后端拒绝启动。
TRUST_PROXY=loopback

# ---- 后台登录防爆破（安全扫描 H-3，依赖 Redis）----
# 单 IP：15 分钟允许的后台登录尝试次数（开发环境同样生效，无豁免）
ADMIN_LOGIN_RATE_LIMIT_MAX=5
# 单账号：15 分钟窗口内连续失败多少次即锁定该后台账号（锁定 15 分钟）
ADMIN_LOGIN_MAX_FAILS=5
# 用户端登录限流（15 分钟窗口），默认 20
LOGIN_RATE_LIMIT_MAX=20
# 应急账号开关：仅 true 时才允许用 ADMIN_USERNAME/ADMIN_PASSWORD 登录（默认关闭，生产保持 false）
ADMIN_EMERGENCY_LOGIN=false

# ---- 令牌吊销 / 服务端登出（安全扫描 H-5，依赖 Redis）----
# 吊销状态「无法确认」时的取向：closed=拒绝服务(503)，open=放行
# 不填时的代码默认：production → closed，其余环境 → open（.env 模板里已显式写出）
AUTH_BLACKLIST_FAIL_MODE=closed
```

> ⚠️ **后台登录锁定依赖 Redis**：`adminLoginGuard` 在 Redis 不可用、命令报错或读写超过 2 秒时**保守拒绝**后台登录（503「登录校验服务暂不可用」），不做 fail-open。因此 Redis 挂掉的表征之一是「管理员登不进后台」——先查 Redis 连通性，再怀疑口令。计数键为 `admin:login:fail:<归一化账号>`，Redis 实例重建/清空即锁定解除；需长期留证请改为独立存储并补审计日志（本轮遗留）。

> ⚠️ **H-5 起 Redis 成为全站鉴权的依赖**：`authMiddleware`、`adminAuth`、`optionalAuth`、Socket 握手四个入口在每次请求都要读一次吊销键（`auth:blacklist:<sha256(令牌)>`、`auth:revoke-user|admin:<id>`）。Redis 不可用、命令报错或读写超 2 秒时按 `AUTH_BLACKLIST_FAIL_MODE` 处理：
> ①`closed`（生产默认）→ 所有需要登录态的接口返回 **503**、写侧（登出/改密/禁用/删号）返回 503 且**不改库**，即「Redis 挂 = 全站登录态不可用」，这是按负责人决策刻意选择的保守取向；
> ②`open` → 放行，但已登出/已被踢的令牌在窗口期内继续有效（吊销形同失效）；
> ③`optionalAuth` 守护的公开接口两种模式下都只降级为匿名，不会 503。
> 运维含义三条：**Redis 必须开持久化并纳入备份**（`auth:blacklist:*` 与两个水位线键只存 Redis，实例重建即「已登出的令牌复活、被踢的会话回来」）；吊销键只在 TTL（最长 30 天）内存在，无需清理任务；`USE_MOCK_DB=true` 的内存 Redis 客户端缺少 `isReady`/`incr`/`ttl`，吊销与短信、防爆破在 mock 模式下一律走「不可确认」分支，本地联调请按环境选择 fail 取向，勿在 mock 环境验证 503 行为。本轮**不新增其它环境变量**。

> ⚠️ **限流按谁计数由 `TRUST_PROXY` 决定（安全扫描 H-8，v6.10）**：`app.set('trust proxy', …)` 决定 `req.ip`，而六个限流器全部以 `req.ip` 为桶。旧实现写死 `1`（无条件信任一跳），任何能直连后端的调用方都能用 `X-Forwarded-For` 每次换一个 IP，登录 20 次/15 分钟、后台 5 次/15 分钟、验证码 1 次/60 秒全部形同不存在，访问日志与 `xn_admin.last_login_ip` 也可被涂抹。现默认 `loopback`，按拓扑取值：

| 拓扑 | 反代位置 | `TRUST_PROXY` 取值 | 说明 |
|------|----------|--------------------|------|
| 传统部署（仓库自带 nginx，同机） | nginx 与后端同机，upstream 走 `127.0.0.1` | 留空或 `loopback` | nginx 用 `$proxy_add_x_forwarded_for` 把真实对端追加在链尾，只信任回环即可取到真实客户端 IP |
| Docker Compose（本仓库默认编排） | nginx 与 backend 分属两个容器，走 bridge 网段 | `loopback,172.16.0.0/12` | 已在 `docker-compose.yml` 的 backend 环境注入（可被宿主 `TRUST_PROXY` 覆盖）。只写 `loopback` 时反代来的流量全共用一个限流桶，全站会被同一个 429 一起限死 |
| 云 LB / K8s ingress / 跨机 nginx | 反代不在这台机器上 | 显式写反代所在网段（如 `10.0.0.0/8`） | 必须显式声明，否则 `req.ip` 是反代 IP，限流退化为「全站共用一个桶」 |
| 后端直接暴露公网、前面没有任何反代 | 无 | `false`（或 `0`/`off`/`none`/`no`） | 完全不信 XFF，`req.ip` 即直连对端；启动日志会告警提示按 IP 限流已退化风险 |

> ⚠️ **`NODE_ENV=development` 不再豁免任何限流（v6.10 行为变更）**：旧实现里五个限流器挂 `skip: nodeEnv === 'development'`，而 `NODE_ENV` 缺省值恰是 `development`，忘设环境变量的生产机器等于没有限流。现在唯一开关是 `RATE_LIMIT_DISABLED=true`，且 `NODE_ENV=production` 时设它后端**拒绝启动**（`server.js` 的 `enforceProductionConfig`）。三条运维影响：①本地/联调会真撞 429，验证码 1 次/60 秒在开发机同样生效，需要放开用 `SMS_RATE_LIMIT_MAX`/`LOGIN_RATE_LIMIT_MAX`/`ADMIN_LOGIN_RATE_LIMIT_MAX`/`RATE_LIMIT_MAX_REQUESTS`，或对本地整体 `RATE_LIMIT_DISABLED=true`；②`tests/e2e/{api-matrix,real-data-smoke,real-data-write}.js` 三个脚本面向开发服务器，运行前必须以 `RATE_LIMIT_DISABLED=true` 启动后端，否则会看到成片 429（见 10 章）；③`TRUST_PROXY` 取值非法（`true`/`*`/`all`、`0.0.0.0/0`、跳数>10、跳数与网段混写、八位组>255、主机位非零网段如 `123.45.67.89/24`）后端在加载配置时直接抛错拒绝启动，启动日志会打印 `🔒 trust proxy = <取值>（来源：env|default）`，容器反复重启先查这一行。遗留：限流计数仍在进程内存（`express-rate-limit` 默认 MemoryStore），多实例/多容器部署时每实例各算一份，阈值实际会按实例数放大，需全站一致要接共享 Redis store（本轮未做）。

**nginx/conf.d/default.conf**（站点配置）：
```nginx
upstream eudazi_backend {
    server backend:3000;        # 容器间通过服务名通信
    keepalive 64;
}

server {
    listen 80;
    server_name _;

    # API代理
    location /api/ {
        proxy_pass http://eudazi_backend;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 60s;
        proxy_send_timeout 60s;
        proxy_read_timeout 60s;
    }

    # WebSocket代理（含 WebRTC 信令）
    location /socket.io/ {
        proxy_pass http://eudazi_backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 86400s;
        proxy_send_timeout 86400s;
    }

    # 前端静态资源
    location / {
        root /usr/share/nginx/html;
        index index.html;
        try_files $uri $uri/ /index.html;
    }

    # ⚠️ 不要写死 X-Forwarded-For $remote_addr：那会丢掉上游代理已经追加的那一段，
    #    多层反代（云 LB → nginx → 后端）下后端 req.ip 只能拿到相邻代理的地址，
    #    「按 IP 计」的六个限流器就退化成全站共用一个桶。
    # 健康检查
    location /health {
        proxy_pass http://eudazi_backend;
        access_log off;
    }
}
```

> **限流与真实客户端 IP（安全扫描 H-8，v6.10）**：上面两段 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` 已经把真实对端追加在链尾，nginx 配置**本轮无需改动**；要配好的是后端的 `TRUST_PROXY`（取值表见 4.1）——写死一跳信任（旧实现）时任何直连后端的调用方都能伪造 XFF 绕过全部按 IP 计的限流，而取值留空/`loopback` 只适配「nginx 与后端同机」的传统部署。本仓库的 compose 编排里 nginx 是另一个容器，`docker-compose.yml` 已注入 `TRUST_PROXY=${TRUST_PROXY:-loopback,172.16.0.0/12}`。部署后验收两步：①启动日志有 `🔒 trust proxy = <取值>（来源：env|default）`；②用移动端网络发一次请求，后端访问日志里的 IP 应是客户端出口 IP 而不是 `127.0.0.1`/`172.16.x.x`（对不上就是信任面配小了，见 12.1 的 429 排查行）。

> **⚠️ 安全响应头必须与 `Cache-Control` 同块声明（安全扫描 M-9，v6.19）**：nginx 的 `add_header` 是**全有或全无**地继承——某 `location`/`server` 只要自带一条 `add_header`，就会**丢弃**上层继承来的全部 `add_header`。因此本仓库把四条基线安全头抽到 `nginx/conf.d/security-headers.inc`（另 443 用 `security-headers-ssl.inc` 在其上补 HSTS），并在**每个自带 `add_header` 的 location**（本仓库为 `/uploads/` 与 `/admin`）里重新 `include` 一次。**自建/修改 nginx 时务必照做**：给某个 `location` 加 `add_header Cache-Control …` 而忘了 `include` 片段，该路径的 `X-Content-Type-Options`/`X-Frame-Options`/`Referrer-Policy`/`CSP` 就会静默消失（修复前 `/uploads/*`、`/admin*` 正处于此状态，443 下还叠加丢了 HSTS）。若使用 nginx ≥ 1.29.3，可改用 `add_header_inherit merge;` 让子层“追加”而非“覆盖”，本仓库镜像 `nginx:1.26-alpine` 尚不支持。`backend/tests/unit/consistency/nginx-security-headers.test.js` 已把「自带 `add_header` 的块必须 reintroduce 片段」固化为静态断言。

```nginx
    location /api/ {

        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_read_timeout 86400s;
        proxy_send_timeout 86400s;
    }

    location /uploads/ {
        alias /data/www/uploads/;
        expires 30d;
        add_header Cache-Control "public, immutable";
        # 审计 M-9：本 location 自带 add_header，会丢弃上层安全头，必须重新引入
        include /etc/nginx/conf.d/security-headers-ssl.inc;
    }
}

# HTTP重定向到HTTPS
server {
    listen 80;
    server_name api.your-domain.com;
    return 301 https://$server_name$request_uri;
}
```

> **传统部署的 `TRUST_PROXY`（安全扫描 H-8，v6.10）**：本节 nginx 与后端同机、upstream 走 `127.0.0.1`，`.env` 里留空或 `TRUST_PROXY=loopback` 即可拿到真实客户端 IP（`$proxy_add_x_forwarded_for` 追加的那一段）。如果 nginx 与后端**不同机**（或前面还有云 LB / CDN / K8s ingress），必须把那一跳的网段写进来（如 `TRUST_PROXY=loopback,10.0.0.0/8`），漏写会让 `req.ip` 恒为相邻代理地址，六个限流器全站共用一个桶——表征是「A 用户触发 429 后 B 用户也登录不了」。跳数写法（`TRUST_PROXY=1`）语法合法但不校验对端来源，直连后端者仍可伪造 XFF，属 H-8 的原始形态，只在确实拿不到反代网段时退而求其次。PM2 场景（8 章）改完 `.env` 要 `pm2 restart` 才生效，验收看启动日志的 `🔒 trust proxy = …` 一行。

## 12. 故障排查

### 12.1 Docker 环境常见问题

| 问题 | 可能原因 | 解决方案 |
|------|----------|----------|
| 容器启动失败 | 端口冲突/资源不足 | `docker compose down` 后检查端口占用 |
| MySQL 启动慢 | WSL2 磁盘性能 | 等待 healthcheck 通过（最多 40s） |
| 后端无法连接 MySQL | 密码不匹配 | 检查 `.env` 和 `docker-compose.yml` 中的密码一致 |
| 后端无法连接 Redis | 服务名/端口不通 | `docker compose exec backend sh` 后 telnet redis 6379 |
| 所有需登录的接口同时返回 503（含后台登录、登出、改密） | 生产 fail-closed 下 Redis 不可达 / 吊销键读写超 2 秒（安全扫描 H-5） | 先看 `/health` 里 redis 段，再查连通性；确认是 Redis 故障可在排障期临时设 `AUTH_BLACKLIST_FAIL_MODE=open` 放行，但已登出/被踢的令牌会立即重新可用 |
| 用户「刚登出又能在别处继续用」/ 被踢会话复活 | Redis 实例被重建或清空（黑名单与水位线只在 Redis） | 恢复持久化/备份；无备份时只能要求全端重新登录并轮换 `JWT_SECRET` |
| Nginx 返回 502 | 后端未就绪 | 等待 `eudazi-backend` 状态变为 healthy |
| 前端构建失败 | Node 版本过低 | 使用 Node 18 LTS |
| `npm install` 慢 | 网络问题 | 配置国内镜像 `npm config set registry https://registry.npmmirror.com` |
| WebRTC 连接失败 | ICE 服务器不可达 | 检查 `WEBRTC_ICE_SERVERS` 配置 |

**存量伪造装扮所有权核查（安全扫描 H-6，只读）**

修复只切断写入侧信任，不改数据。改造前客户端可以把任意装扮写进 `xn_user_pref.data.skinShop.owned`，其中**在目录内**的条目现在仍视为已拥有。是否回收由产品决策，先跑只读核查评估面：

```sql
-- 列出 skinShop.owned 中含 true 的记录（data 是 TEXT，JSON_EXTRACT 走隐式解析，非法 JSON 回 NULL 不报错）
SELECT p.user_id, u.lv, u.money, p.update_time,
       JSON_EXTRACT(p.data, '$.skinShop.owned') AS owned
FROM xn_user_pref p
JOIN xn_user u ON u.id = p.user_id
WHERE p.data LIKE '%skinShop%'
  AND CAST(JSON_EXTRACT(p.data, '$.skinShop.owned') AS CHAR) LIKE '%true%'
ORDER BY p.update_time DESC;
```

判定「哪些键在目录内」只能对照 `backend/src/utils/skinCatalog.js`（26 件，键形如 `frame_sf8`/`badge_sb6`/`bubble_sbbl6`/`theme_sth6`），库里没有对应的表可 JOIN。**不要**直接 `UPDATE ... SET data = JSON_REMOVE(...)`：`data` 是 TEXT 且承载其它偏好键，写坏一次会让用户整份偏好解析失败（服务端按 `{}` 兜底，表现为「所有设置被清空」）。需要回收时请在事务里整段读出、按目录重写、先备份该表。

## 12.5 COS 防盗链与 CORS 配置（必做）

前端直传 COS 与「带签名访问 URL」方案依赖以下控制台配置，否则会出现跨域 403 或资源被盗刷：

### 1) CORS 跨域配置（前端直传/签名访问必须）
- 进入「对象存储」→ 选择 Bucket → 「安全管理」→「跨域访问 CORS 设置」。
- 新增规则：
  - 来源 Origin：`https://你的前端域名`（开发可临时加 `http://localhost:5173`）
  - 操作 Methods：`PUT`、`GET`、`POST`、`HEAD`
  - Allow-Headers：`*`（至少包含 `Content-Type`、`Authorization`）
  - 暴露 Headers：`ETag`
  - 超时 Max-Age：600

### 2) 防盗链 referer 白名单（防带宽盗刷）
- 进入「对象存储」→ 选择 Bucket → 「安全管理」→「防盗链设置」。
- 开启「防盗链」，referer 白名单填写：`https://你的域名/*`（及 `https://cdn.你的域名/*` 若有 CDN）。
- 空 referer 策略：建议「拒绝」（公开资源可放行，按需）。
- 该策略须与 Nginx `/uploads/` 的 `valid_referers` 保持一致（本地静态已配置 referer 校验，非白名单返回 403）。

### 3) 访问签名 URL（代码已内置）
- 后端 `cosSignedUrlService` 在返回动态/相册媒体时自动生成带时效的 GET 预签名 URL（默认 600s）。
- 如需调整时效，设置环境变量 `COS_SIGNED_URL_EXPIRES`（秒）。

> 以上 1)、2) 必须在腾讯云控制台手动完成，代码无法替代；3) 已由后端自动处理。
