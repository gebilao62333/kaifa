## P0 资金与核心链路阻断（建议先修）

### P0-1 充值下单 / 回调整链字段错位（`xn_order_chong`）

**位置**
- `src/services/payService.js` → `createOrder`、`wxPayCallback`、`getPaymentHistory`
- `src/services/wechatPayService.js` → `createUnifiedOrder`、`handleNotify`

**现状（对照 `OrderChong` 模型 = `xn_order_chong` 表）**

表真实列：`order_no, user_id, amount(NOT NULL), coins(NOT NULL), status, pay_type, pay_time, create_time, update_time`。**没有** `cid / money / gold_coins / currency / pay_no`。

| 代码位置 | 写入/读取 | 问题 |
|---|---|---|
| `payService.createOrder` | `cid, money, gold_coins, currency` | 未知字段被 Sequelize 忽略；NOT NULL 的 `amount`、`coins` 未写 |
| `wechatPayService.createUnifiedOrder` | `cid, money` | 同上 |
| `payService.wxPayCallback` | `pkg = RechargePackage.findByPk(order.cid)` | `order.cid` 为 undefined → `pkg` 为 null → `pkg.coins` 抛错 |
| `wechatPayService.handleNotify` | `order.cid`、`order.update({pay_no})` | 同样读不到套餐；`pay_no` 列不存在 |
| `payService.getPaymentHistory` | `order.money`、`order.gold_coins` | 字段不存在，返回 undefined |

**影响**：`POST /api/pay/create-order`、`/wx-order`、`/pay/create` 触发 `SequelizeValidationError: notNull Violation`（500）；即使建单成功，回调也无法加币。

**修复方案**（最小改动，不改表）
1. `createOrder` / `createUnifiedOrder` 写：
   ```js
   amount: Number(pkg.price),
   coins: pkg.coins + (pkg.bonus_coins || 0),
   pay_type: payType,
   status: 0
   ```
2. 回调不再反查套餐，直接用订单自身金币入账：
   ```js
   await order.update({ status: 1, pay_time: getTimestamp() }, { transaction });
   await User.increment('money', { by: order.coins, where: { id: order.user_id }, transaction });
   ```
   （`transactionId` 当前无处存。可选：临时记到 `pay_type` 之外的新列，或本次先不记录，作为增强项。）
3. `getPaymentHistory` 改读 `order.amount`、`order.coins`。

**复现/验证**：`POST /api/pay/create-order {packageId}` 应返回 `orderNo`；`POST /api/pay/wx-callback {payNo, transactionId}` 后查 `xn_user.money` 增加 `coins`。

> ⚠️ 本条验证步骤已过时（2026-10-05 安全扫描 H-2 起）：`/wx-callback` 现在**必须带登录态**且只能由下单人本人调用，
> 服务端还要求微信支付参数已配置并能反查到 `trade_state=SUCCESS`（未配置时一律 403），
> 因此这条链路只能在配置了真实商户参数、或显式开启 `ALLOW_UNVERIFIED_PAY_CALLBACK=true`（非生产）的环境下复现。
> 现行口径见《后端API接口文档》5.9「支付入账口径」。

### P0-2 提现两条链路 NOT NULL 缺失（`xn_withdraw`）

**位置**：`src/services/giftService.js#withdraw`、`src/services/walletService.js#applyWithdraw`；模型 `Withdraw`。

**现状**：`money`、`amount`、`pay_money` 三列均 `allowNull:false`。

| 入口 | 写了 | 漏了（NOT NULL） |
|---|---|---|
| `giftService.withdraw`（礼物提现） | money、pay_money、shouxufei | **amount** |
| `walletService.applyWithdraw`（钱包提现） | amount、type、account… | **money、pay_money** |

**影响**：两处 INSERT 均触发 notNull 校验失败，**提现申请完全不可用**。

**修复方案**：抽一个内部函数统一落单，三列齐写，避免再次漂移：
```js
const createWithdrawRecord = (data, options) => Withdraw.create({
  user_id, 
  money: amount,          // 提现额
  amount,                 // 提现额（历史冗余列）
  pay_money: netAmount,   // 到账净额
  shouxufei: fee, type, account, bank, name, image, mobile,
  is_check: 0, status: 0, channel,
  create_time: getTimestamp(), update_time: getTimestamp()
}, options);
```
两个入口都改调它。

**验证**：`POST /api/gift/withdraw` 与 `POST /api/wallet/withdraw` 各提交一次，检查 `xn_withdraw` 落行且三列有值。

### P0-3 钱包收入聚合字段错位（礼物 / 通话）

**位置**：`src/services/walletService.js#collectIncomeRecords`

**现状**

| 业务 | 现有 SQL | 真实列 | 问题 |
|---|---|---|---|
| 礼物 | `total_money AS amount … WHERE to_user_id` | `totalmoney`、`user_id`（收款人） | 列名全错 |
| 通话 | `b.amount`、`b.call_record_id`、`r.type`、`b.status=1` | `b.total_amount`、`b.call_id`、`r.call_type` | 列名错 |

**影响**：`/api/wallet/overview`、`/income-records`、`/income-breakdown` 恒缺礼物与通话收入，总资产偏小。

**修复方案**
```js
// 礼物（收款人为 xn_gift_log.user_id）
'SELECT id, totalmoney AS amount, create_time FROM xn_gift_log WHERE user_id = :uid'

// 通话
`SELECT b.id, b.total_amount AS amount, b.create_time, r.call_type
 FROM xn_call_billing b
 JOIN xn_call_record r ON b.call_id = r.id
 WHERE r.callee_id = :uid AND b.status = 1`
// call_type === 2 ? video : voice
```
**配套（关键）**：`src/services/callBillingService.js#createBilling` 目前写 `status: 0`，且**无人**把它改为 1，导致上面查询恒为空。由于该方法在扣款/分账的同一流程里完成，应改为 `status: 1` 并写 `settle_time`（语义=已结算）。**需先与产品确认"通话收入何时计入"**：即时入账（推荐，与现有资金流一致）还是审核后入账。

**验证**：送一次礼物 + 完成一次「陪玩通话」后，`/api/wallet/income-records` 出现礼物与通话条目。

## P1 安全

### P1-1 管理端权限兜底 `['all']`
- **位置**：`src/controllers/adminManage.js`（`resolvePermissions` / `adminLogin`）、`src/utils/permissions.js`
- **现状**：无角色且账号权限为空 → 兜底全权限；DB 异常时回退环境变量账号并给 `['all']`。
- **修复**：兜底改为 `[]`；仅 `is_super` 或 `role_id===1` 给全权限；环境变量应急账号加显式开关（如 `ADMIN_EMERGENCY_LOGIN=true`）且默认关闭。
- **验证**：建一个无角色无权限账号，登录后访问管理接口应 403。
- **补充（2026-10-05，安全扫描 M-1）**：本项的「兜底」视角只覆盖了「读」，没覆盖「写」——`/api/admin-manage` 的七个写接口（`POST /admins`、`PUT /admins/:id`、`PUT /admins/:id/password`、`DELETE /admins/:id`、`POST /roles`、`PUT /roles/:id`、`DELETE /roles/:id`）此前只挂 `requirePermission('admin:write')`，任何持该权限的管理员都能往 `permissions` 写 `['all']`（`isSuperAdmin` 见 `all` 即全权限）或把 `role_id` 改成 1 自提为超管，还能重置超管密码、经 `PUT /roles/:id` 改写超管角色凭证。本轮在 `utils/permissions.js` 新增 `permissionsBeyondActor`/`canManageRole`/`canManageAdmin` 三个纯函数，七个处理器全部接入「授权边界（授予集 ⊆ 操作者自身）+ 对象边界（目标不得为超管位、有效权限不得超出操作者）」两级校验，越界一律 403；`POST /admins` 始终按有效角色（缺省 2）校验，不传 `role_id` 不再是旁路；改密/删除的边界检查先于 H-5 吊销动作。行为变更：非超管的越界提交由「成功」变 403（管理端 `common.js` 透传文案，无需发版）。遗留：权限/角色是登录时快照，改完不吊销在用令牌需重新登录；应急账号登录即全权限不受此约束。详见《后端交互功能梳理》发现第 22 条、《后端开发文档》v6.17。
- **补充（2026-10-05，安全扫描 M-2）**：M-1 与更早的兜底修复都建立在同一个前提上——`adminAuth` 只读令牌内声明，而管理端令牌是**登录时刻快照**且时效硬编码 `7d`，于是「改权限/换角色」（刻意不吊销以免自踢）最长 7 天才生效，「禁用/删号」（有 H-5 吊销）在非生产 fail-open 时也留有空窗。本轮三处收口：①`config/index.js` 新增 `adminExpiresIn`（`ADMIN_JWT_EXPIRES_IN`，默认 `12h`），`controllers/admin.js` 与 `controllers/adminManage.js` 共 6 处签发统一改传；②令牌 payload 新增 `adminScope`（`account`/`role`/`emergency`）——`xn_admin`/`xn_admin_role` 两表 id 独立自增会碰撞，回读需要它判断目标表；③`middlewares/auth.js` 新增 `resolveLiveAdmin`，`adminAuth` 每请求回读：已删除/旧格式（无 `adminScope`）→ 401「令牌已失效」，`status≠1` → 403「账号已被禁用」，`role_id`/`permissions` 一律取库内当前值——**改权限/换角色/禁用/删号下一个请求即生效**（M-1 补充里「需被改者重新登录」一句被本项覆盖）。回读失败沿用 `tokenRevocation.revocationFailMode()`（生产 fail-closed 503 / 非生产按令牌快照放行并告警）。分工不变形：改密后旧令牌收口仍**只**靠 H-5 吊销水位线（回读不校验口令版本）；删号/禁用为「吊销 + 回读」双保险。行为变更：存量管理员令牌（无 `adminScope`）一律 401，管理员需重新登录一次（与 H-4 口径一致，C 端不受影响）；管理端 `common.js`/`router/index.js` 对 401/403 本就清态跳登录，前端零改动。遗留：payload 内权限快照保留（仅非生产回退用）；`admin_refresh` 仍无消费入口；`ADMIN_TOKEN` 不可吊销；管理端 UI 菜单显隐读 `localStorage.admin_user`、权限变更后显示滞后到下次登录（接口侧已实时，属前端待办）；共用 `JWT_SECRET`/声明放行/非常量时间比对属 M-3。详见《后端交互功能梳理》发现第 23 条、《后端开发文档》v6.18。

## P3 健壮性与并发

### P3-1 扣费类并发无锁 / 无事务
- **位置**：`gamesService#createOrder`（先查余额再扣）、`#grabOrder`、`reserveService#createReserve`、`circleService#unlockPost`
- **修复**：统一改为事务 + 原子 UPDATE：
  ```sql
  UPDATE xn_user SET money = money - :amt WHERE id = :uid AND money >= :amt;
  ```
  以 `affectedRows` 判定成功；唯一键冲突（如 `xn_post_unlock` 的 `post_id+user_id`）改为**先写解锁记录再扣费**或捕获冲突回滚，避免"钱已扣、记录未落"。
- **补充（2026-10-05，安全扫描 H-7）**：批次 4 只把「原子 UPDATE + `affectedRows`」用在**扣款**上，**状态迁移本身仍是读后改**，因此同一笔钱可以被第二次操作再动一次。本轮补齐的口子：
  - `reserveService#cancelReserve`（`status∈(0,1)` 读后 `update(4)` 再按比例退款 → 并发双退）、`#completeReserve`（`1→3` 后分账 → 并发双分账，且 `reserve_commission_rate` 在事务外读取）；
  - `reserveService#confirmReserve`／`#rejectReserve`（后者原来**完全无事务**，"改单 + 释放时段"两次独立写，中途失败留下"已拒绝但时段仍占用"）、`#toggleSlot`（`0 ⇄ 2` 无条件取反，会把已成交 `status=1` 的时段翻回可约，凭空释放预约位）；
  - `gamesService#startOrder`／`#completeOrder`（同 `completeReserve`，另含 `xn_companion_profile.income_total/order_num` 的读-改-写）、`#appealOrder`（`1|2|3→5`）、`#evaluateOrder`（重复评价把同一单计入滚动平均分两次）。
  - **统一口径**：`Model.update(新状态, { where: { id, status: 前态, 归属列 }, transaction })` + 影响行数判定，抢占成功后**在同一事务内**才动钱；聚合列（`income_total/order_num/star/pingjia_num`）先 `SELECT ... FOR UPDATE` 锁行再重算。之所以不用 `instance.save()`，是 Sequelize 无法把「前态」写进 `UPDATE ... WHERE`。
  - **仍属本条未覆盖**：`/api/games/toggle-service`（`profile.status 2 ⇄ 3`）仍是读后改，因不涉及资金与聚合列本轮未动；`appealOrder` 翻到 5 后不冲结算，金额需后台人工处理；无请求级幂等键。详见《后端开发文档》v6.14、《数据库设计文档》v6.18 §2.2.2/§2.3.1/§2.3.2。
