> v6.27 变更: 安全扫描 M-8 修复（实名 PII 明文存储 + `utils/crypto.js` 死代码 + 手机号明文日志 + `password` 无 `select:false`）**有表结构变更（仅加宽列，无新增/改名/删列）、无新增/改动 Redis 键；新增 1 个手动迁移**。①**列宽变更**：`xn_user` 的 `real_name` VARCHAR(50→**255**)、`id_card` VARCHAR(18→**255**)、`real_name_front` VARCHAR(255→**512**)、`real_name_back` VARCHAR(255→**512**)，以容纳 AES-256-GCM 密文（长度 ≈ `salt128 + iv32 + tag32 + 明文字节×2`，HEX）。由**手动迁移** `src/migrations/20261004000002_widen_pii_columns.js` 执行（幂等：查 `INFORMATION_SCHEMA.CHARACTER_MAXIMUM_LENGTH`，已加宽跳过；**不注册进 `runMigrations`**，与既有 `20261003000002_widen_user_id_and_ip.js` 同约定）——**上线硬顺序：先跑迁移加宽列，再配置 `PII_ENCRYPTION_KEY` 并重启后端**，顺序反了密文会被旧列宽截断。②**存储形态变更**：上述四列改存密文（密钥 `PII_ENCRYPTION_KEY`，`config.pii.encryptionKey`；生产未配置/弱值 → `server.js` 致命项拒绝启动），读取时 `utils/pii.js` 的 `decryptField` 先判别（`looksEncrypted`：全十六进制且长度 ≥192）——**判别为假的存量明文原样返回**，本轮**不做数据回填**；换键后旧密文不可解（`decryptField` 捕获异常按空值处理并告警），**无密钥轮换机制（遗留）**。③**`password` 列的默认可见性**（ORM 层，非 MySQL 约束）：`models/mysql/User.js` 新增 `defaultScope: { attributes: { exclude: ['password'] } }` + `scopes: { withPassword: { attributes: { include: ['password'] } } }`——所有默认查询不再带出口令哈希，登录/改密经 `User.scope('withPassword')` 显式取回；**MySQL 侧的列定义与索引未变**，`password` bcrypt 哈希本身仍是明文列（不可逆哈希，非法定意义上的 PII 加密项）。④**手机号仍明文**：`mobile`（`unique`）是登录/注册的等值查号键，**加密后无法按等值查询**，须另存一列「盲索引」（`sha256(mobile + salt)`）方能加密，本轮不改结构，登记为**遗留**。⑤数据层面：不新增/改名/删列、不建索引、不回填、不动存量行（存量实名行仍是明文，由 ②的判别逻辑兼容读取）。**行为变更**：配置密钥后新提交的实名四字段落库为密文；未配置密钥的非生产仍明文（仅告警）；生产未配密钥**拒绝启动**。**DBA 核查（可选，只读）**：`SELECT id, CHAR_LENGTH(real_name), real_name FROM xn_user WHERE real_name IS NOT NULL AND real_name != '' LIMIT 50` 可区分存量明文与新增密文（密文行长度为 ≥192 的纯十六进制）。本轮新增迁移 `20261004000002_widen_pii_columns.js`；新增测试因本机无 node/npm **未执行**，仅静态复核。详见《后端开发文档》v6.23、《后端API接口文档》v6.25.0
> v6.26 变更: 安全扫描 M-7 修复（红包并发超额发放）**无表结构变更、无新增/改动 Redis 键、无迁移、无数据改动**——本轮改动全在 `services/giftService.receiveRedPacket` 的事务与锁定语义：①**改了什么**——领取红包由「事务外读红包 + 事务内条件更新占位」改为「单事务内先 `SELECT ... FOR UPDATE` 锁定 `xn_red_packet` 行、再按最新 `remain_num`/`remain_amount` 计算并分配金额」；金额以「分」为单位计算，拼手气为其余人各留 ≥1 分、最后一人取剩余全部，普通红包均分不足留给最后一人；`remain_amount` 递减改用 `moneyMinus`（不再 `GREATEST` 夹值）。②**为什么与本层相关**——原实现只保证「名额不被抢成负数」，**不保证「金额不超额」**：并发请求基于各自读到的旧 `remain_amount` 取随机金额，`GREATEST(remain_amount - amount, 0)` 把剩余额夹到 0 时，多出的部分仍照常写入 `xn_user.money`，即**从 `xn_user.money` 多发出了钱**（同一红包累计领取可超过 `total_amount`）；锁定行后同一红包的领取串行化，`total_amount = Σ已领 + 关闭时剩余(0)` 成立。③**列/索引零改动**——`xn_red_packet`（`packet_no` 唯一、`id` 主键）与 `xn_red_packet_log` 的 `(packet_id, user_id)` 唯一索引（迁移 `20261003000001` 建立）均不动，行锁与 `ER_DUP_ENTRY` 兜底都建立在既有结构上。④**契约对齐**——`/api/gift/redpacket/receive` 请求字段以 `packetNo` 为准（前端 `giftService.receiveRedPacket` 由 `packetId` 改名对齐），边界层校验 `packetNo` 必填字符串 1~64。**数据层面零改动**：不新增/修改列、不回填、不动存量红包行与领取记录；**存量数据核查（可选，DBA 侧）**：`SELECT packet_id, SUM(amount) s FROM xn_red_packet_log GROUP BY packet_id` 与 `SELECT id, total_amount FROM xn_red_packet` 对账即可发现改造前是否发生过超额（`SUM(amount) > total_amount`），本轮**不改写历史数据**。**行为变更**：并发抢同一拼手气红包不再超发；普通红包零头由最后一名领取者获得（原被清零少发）。**遗留**：C 端红包气泡无领取入口（`ChatRoom.vue`）、前端 `receiveRedPacket` 全仓库无调用方，属前端待办；红包记录接口 `GET /api/gift/redpacket/history` 未分页。本轮无迁移脚本、无需重建 Redis；改写 `tests/unit/services/giftService.test.js` 的 `receiveRedPacket` describe 因本机无 node/npm **未执行**，仅静态复核。详见《后端开发文档》v6.22、《后端API接口文档》v6.24.0

**状态机与并发口径（v6.18，安全扫描 H-7）**

| 迁移 | 入口 | 写入条件（`WHERE`） | 抢占成功后才做的事 |
|------|------|--------------------|--------------------|
| `0 → 1` | `grabOrder` 抢单 | `id AND status=0` | 写 `target_user_id / companion_id / companion_name / add_time` |
| `1 → 2` | `startOrder` 开始服务 | `id AND target_user_id AND status=1` | 无资金动作 |
| `2 → 3` | `completeOrder` 完成 | 事务内 `id AND user_id AND status=2` | `amount`=服务端算出的到手收入、`user_time/end_time`；买家退款不在此路径；陪玩师 `gift_money`/`gift_money_zong` 累加、`xn_companion_profile` 的 `income_total/order_num` 在**同一事务**内 `SELECT ... FOR UPDATE` 锁行后重算；提交后才 +50 经验 |
| `0\|1 → 4` | `cancelOrder` 取消 | 事务内 `id AND status IN (0,1)` | 退金币 `User.increment('money')` |
| `1\|2\|3 → 5` | `appealOrder` 申诉 | `id AND user_id AND status IN (1,2,3)` | 写 `appeal_reason/appeal_time`（**不冲结算**，已分账金额不回滚） |
| 评价 | `evaluateOrder` | 事务内 `FOR UPDATE` 重读订单行，要求 `status=3 AND user_id=本人 AND pingjia_status=0` | 写 `star/content/pingjia_status/pingjia_time`，并锁 `xn_companion_profile` 行后重算滚动平均分 |

口径要点：判据用 `Model.update` 返回的**影响行数**（Sequelize 的 `instance.update()` 无法把「前态」写进 `WHERE`），落败方读到 0 行即抛错回滚，因此同一单的退款、分账、平均分只会被执行一次；抽成比例 `order_commission_rate` 的读取也已移入该事务，避免「读到旧比例、写入新金额」的快照错位。

**状态机与并发口径（v6.18，安全扫描 H-7）**

| 迁移 | 入口 | 写入条件（`WHERE`） | 抢占成功后才做的事 |
|------|------|--------------------|--------------------|
| 建单 `status=0` | `createReserve` 预约 | 同事务内先 `UPDATE xn_reserve_slot SET status=1 WHERE id=? AND status=0` 抢时段 | 查重(有效单)→`UPDATE xn_user SET money=money-price WHERE id=? AND money>=price`→建单 |
| `0 → 1` | `confirmReserve` 确认接单 | `id AND target_user_id AND status=0` | 无资金动作 |
| `0 → 2` | `rejectReserve` 拒绝 | 事务内 `id AND target_user_id AND status=0` | 同事务释放时段：`UPDATE xn_reserve_slot SET status=0 WHERE user_id=? AND reserve_date=? AND reserve_time=? AND status=1`（改造前这段完全在事务外） |
| `0\|1 → 4` | `cancelReserve` 取消 | 事务内 `id AND user_id AND status IN (0,1)` | 释放时段（同上，只命中 `status=1`）→按距开始时间比例退款（≥24h 全退、≥12h 退 50%、否则不退）`User.increment('money')` |
| `1 → 3` | `completeReserve` 完成 | 事务内 `id AND status=1 AND (user_id=? OR target_user_id=?)` | 先算 `companionIncome = price × reserve_commission_rate`（比例在事务内读）→`User.increment('gift_money'/'gift_money_zong')`；**不写陪玩师资料表**，也不释放时段 |

口径要点：动钱的两个迁移（`→4` 退款、`→3` 分账）都是**先抢占状态、再在同一事务内打款**，影响行数为 0 直接抛「预约无法取消 / 预约状态不正确，仅可完成已确认的预约」并回滚——改造前是「`findByPk` 判状态 → `update` → `increment`」的读后改，两个并发请求会各退一次款、各分一次账。

| 迁移 | 入口 | 条件 |
|------|------|------|

**入账的状态机与幂等（安全扫描 H-2，v6.13）**

- 唯一的合法迁移是 `0 → 1`，由 `payService.settleRechargeOrder` 在事务内以一条条件 UPDATE 完成：
  `UPDATE xn_order_chong SET status=1, pay_time=?, update_time=? WHERE id=? AND status=0`，随后检查影响行数。
  InnoDB 下并发重发的第二笔会等行锁释放后重新判定 `status=0`，得到 `affected=0` 而不加币——
  这是「同一笔充值只到账一次」的**唯一**保证，与 `xn_card` 核销的 `status=0` 条件原子占用同一套做法。

- 查询订单一律带 `user_id`（`getOrderStatus` / `requireOwnedOrder`），避免凭订单号读他人支付状态。
- **缺列（遗留）**：没有第三方流水号列（微信 `transaction_id`）、也没有支付宝渠道单号列，

  注意**不能**建 UNIQUE——同一笔平台流水在极端情况下可能对应多条本地单，唯一约束会让补单写入直接失败）。
- 审计用 SQL（查是否存在同一订单被重复加币的痕迹，正常应恒为 0 行）：
  ```sql
  SELECT order_no, COUNT(*) c FROM xn_order_chong GROUP BY order_no HAVING c > 1;
  ```

| `gift` | `gift_money` + `money`（同一事务，任一未命中整单回滚） | `gift_money` + `money` | 不再动余额 |
| `admin` | `money` | `money` | 不再动余额 |

- `xn_user.money` 是唯一的**真实余额**：所有收入（接单 / 礼物 / 语音视频通话 / 私密帖解锁 / 红包 / 预约）与充值都入账到它，消费（下单、VIP、解锁、装扮、发红包、送礼物）从它扣减，提现也从它扣减。
- `xn_user.gift_money` 是「礼物收益中尚未提现的额度」，只做可提现上限与统计；`gift_money_zong` 是累计礼物收益。
- **本版本无表结构变更**，改的是读写口径：历史实现 wallet 渠道只写申请单、不扣 `money`，「总资产」由 `xn_game_order`/`xn_gift_log`… 聚合派生（既不含已消费也不含充值），同一笔钱可花可提，属资损。
- ⚠️ 存量数据：v6.10 之前处于待审核（`is_check=0`）的 wallet 提现单是按「未扣款」口径建的，若在新逻辑下驳回会多退一笔 `money`——需人工核对存量，本轮未做数据修补。

### 2.10 通话模块

#### 2.10.1 通话记录表 (xn_call_record)

> 本表同时是 **TRTC 通话房间的权限真相来源**（安全扫描 C-4，v6.12）：项目没有独立的房间表，
> `trtc_room_id` + `caller_id` + `callee_id` 就是房间成员名单。`trtcService.resolveRoomCall` 按
> `WHERE trtc_room_id = ? ORDER BY status ASC, create_time DESC` 取单，只有主叫/被叫且
> `status ∈ {0,1}` 才能拿到进房票据，详见《后端API接口文档》11.4。

| 字段名 | 类型 | 说明 | 约束 |
|--------|------|------|------|
| id | INT | 主键 | PK, AUTO_INCREMENT |
| call_no | VARCHAR(50) | 通话编号(callNo)，`generateCallNo()` 生成 | UNIQUE(`idx_call_no`), NOT NULL |
| caller_id | INT | 主叫用户ID(callerId) | NOT NULL |
| callee_id | INT | 被叫用户ID(calleeId) | NOT NULL |
| call_type | TINYINT(1) | 类型 1-语音 2-视频(callType) | NOT NULL |
| trtc_room_id | INT | TRTC 房间号(trtcRoomId)，进房票据的查询键 | NOT NULL，普通索引 `idx_trtc_room_id`（**非唯一**，见下方说明） |
| status | TINYINT(1) | 状态 0-呼叫中 1-已接通 2-被拒绝 3-主叫取消 4-已结束 5-无应答 | DEFAULT 0 |
| connect_time | INT(10) | 接通时间(connectTime，接听时写入，用于算时长) | DEFAULT 0 |
| end_time | INT(10) | 结束时间 | DEFAULT 0 |
| duration | INT | 通话时长(秒) | DEFAULT 0 |
| end_reason | VARCHAR(100) | 结束原因：`normal` / `caller_cancel` / `callee_reject` / `unanswered_hangup` | NULL |
| is_companion_call | TINYINT(1) | 是否陪伴通话（1 才在结束时计费） | DEFAULT 0 |
| order_id | BIGINT | 关联陪玩订单ID | DEFAULT 0 |
| create_time | INT(10) | 创建时间 | DEFAULT 0 |

索引：`idx_call_no`(UNIQUE)、`idx_caller_time`(caller_id, create_time)、`idx_callee_time`(callee_id, create_time)、
`idx_status_time`(status, create_time)、`idx_order_id`、`idx_trtc_room_id`。

**`trtc_room_id` 为什么不建 UNIQUE**：房间号在 TRTC 侧是可复用的短期标识，历史通话结束后同一号码可被再次分配；
唯一约束会让「复用旧号」直接插入失败。改为在应用层避免**并发**冲突——
`callBillingService.allocateTrtcRoomId()` 用 `crypto.randomInt(1, 1000000)` 生成候选号，
并对 `status ∈ {0,1}` 的进行中通话查重后占用（最多重试 5 次）。
旧实现是 `Math.floor(Math.random()*1000000)+1` 且不查重，两通电话撞同一个号即互相串音串画；
因此**存量数据可能存在重复号**，`resolveRoomCall` 用 `ORDER BY status ASC` 优先命中进行中的通话来兼容，
若同一号上有两通都在进行的旧数据，后到的那方会被判 403（失败方向是安全的），需要清理时可按下句核对：
`SELECT trtc_room_id, COUNT(*) FROM xn_call_record WHERE status IN (0,1) GROUP BY trtc_room_id HAVING COUNT(*)>1;`

**安全口径（v6.11，安全扫描 C-3）**
- 兑现凭证是「`card_no` + `card_password`」双项（密钥链路为 `card_key` 单项），服务端此前只比卡号、密码从不参与，等于拿到卡号即可入账。
- `card_password` 仍**明文落库**：`GET /api/admin/cards` 需要把密码展示给发卡方，故本轮只在服务层改为 sha256 摘要 + `crypto.timingSafeEqual` 恒定时间比对，加密存储列为遗留。
- 三件套的生成熵：卡号 `DK` + 14 位、密码 12 位（各 32 字符集，≈70/60 bit），密钥 25 位数字（≈83 bit），全部 `crypto.randomInt` 逐字符取样；旧实现用 `Math.random`（内部状态可复现）且卡号以 `Date.now()` 的 base36 开头，已知发卡时间即可大幅压缩猜测空间——**历史已发卡密建议作废未售存量后重新发放**。

>
> 存量核查 SQL（找出改造前伪造的所有权，本轮**不清退**，只供人工评估）：
>
> ```sql
> -- MySQL 5.7+：列出 data.skinShop.owned 中已为 true 的用户与键
> SELECT p.user_id,
>        u.money,
>        u.lv,
>        p.update_time,
>        JSON_EXTRACT(p.data, '$.skinShop.owned') AS owned
> FROM xn_user_pref p
> JOIN xn_user u ON u.id = p.user_id
> WHERE p.data LIKE '%skinShop%'
>   AND JSON_EXTRACT(p.data, '$.skinShop.owned') IS NOT NULL
>   AND CAST(JSON_EXTRACT(p.data, '$.skinShop.owned') AS CHAR) LIKE '%true%'
> ORDER BY p.update_time DESC;
> ```
>
> 注意 `data` 是 `TEXT` 而非 `JSON` 列，`JSON_EXTRACT` 会先做隐式解析，遇到历史上写坏的非法 JSON 返回 `NULL` 而不报错，因此 `LIKE '%skinShop%'` 那一条只是缩小扫描面，不能替代逐行核对；目录内键与已下架键的区分只能由 `utils/skinCatalog.js` 判定，SQL 里没有对应表可 JOIN。

#### 8.3.1 Redis 非缓存键（认证与安全）

这些键不在 MySQL 里，却是登录/认证链路的状态真相来源，DBA 排障时必须知道它们存在：

| 键 | 写入方 | TTL | 语义 |
|----|--------|-----|------|
| `auth:blacklist:<sha256(令牌原文)>` | `services/tokenRevocation.js`（安全扫描 H-5，v6.16） | 令牌剩余寿命（`exp - now`），上限 `JWT_REFRESH_EXPIRES_IN` | 单令牌拉黑（登出当前设备）。**v6.15 之前的旧键是 `blacklist:<token>` 且全仓库没有写入点**——只有 `authMiddleware` 在读，等于「登出」从不生效；现键名放 SHA-256 摘要而非原文，因为原始 JWT 是可直接复用的凭据，放进键名会出现在 `MONITOR` 输出、`KEYS` 结果与 RDB 备份里 |
| `auth:revoke-user:<userId>` | `services/tokenRevocation.js`（H-5） | `JWT_REFRESH_EXPIRES_IN`（默认 `30d`） | 用户「全端下线」水位线，值为 `now+1` 秒；`iat` 早于它的令牌一律作废。触发点：重置密码、登出带 `logoutAllDevices`、后台封号（尽力而为） |
| `auth:revoke-admin:<adminId>` | `services/tokenRevocation.js`（H-5） | `JWT_REFRESH_EXPIRES_IN` | 管理员全端下线水位线。触发点：改管理员口令、删除管理员、禁用管理员（`status≠1`）——`adminAuth` 不回查 `xn_admin`，这些改库动作本身踢不掉在用令牌，水位线是唯一收口 |
| `sms:code:<scene>:<mobile>` | `services/smsService.js` | 300 秒（`SMS_EXPIRE`） | scene ∈ login/register/reset，三类各自独立（v6.9） |
| `sms:cooldown:<scene>:<mobile>` | `services/smsService.js` | 60 秒（`SMS_COOLDOWN`） | 同场景重发冷却 |
| `sms:fail:<scene>:<mobile>` | `services/smsService.js` | 300 秒，与验证码同有效期 | 连续 5 次校验失败即删除 code + fail 两键作废该码；Redis 取数失败同样按「拒绝」处理 |
| `admin:login:fail:<归一化账号>` | `services/adminLoginGuard.js`（安全扫描 H-3，v6.14） | 15 分钟，仅首次失败时 `EXPIRE` | 后台登录连续失败计数，达 `ADMIN_LOGIN_MAX_FAILS`（默认 5）即锁该账号；账号名先 `trim().toLowerCase()`，不存在的用户名同样计数；登录成功即 `DEL` |

⚠️ 四点运维含义：①`admin:login:fail:*` 与三个 `auth:*` 键都只在 Redis，**Redis 实例重建/清空即状态丢失**（锁定被解除、已登出令牌与已下线主体全部复活），故 Redis 必须开持久化并纳入备份；②H-5 起 **Redis 不可用不再等于跳过检查**：`getRedisClient()` 只返回 `isReady` 的客户端，取不到、命令报错或读写超 2 秒都算「无法确认」，生产默认 **fail-closed → 所有需登录接口 503**（`optionalAuth` 例外，按匿名处理），可用 `AUTH_BLACKLIST_FAIL_MODE` 临时改取向——即 Redis 故障的表征是「全站掉线」而非「静默放行」；③`USE_MOCK_DB=true` 的内存 Redis 客户端没有 `isReady` 且缺 `incr`/`ttl`，`getRedisClient()` 因此返回 `null`，mock 模式下短信验证码、后台防爆破与令牌吊销**全部不可用**（写入侧走 fail-open，只回 `devicesRevoked:false`），需要真实 Redis 才能验证这些链路；④键里没有密码学材料，但 `auth:blacklist:*` 的键名是令牌摘要——摘要本身泄漏后也无法反推令牌，账号名仍以明文小写进入键名，日志与监控导出时注意。

### 8.4 数据安全

1. **敏感字段加密**: password字段使用bcrypt加密
2. **定期备份**: 每日全量备份,每小时增量备份
3. **权限控制**: 遵循最小权限原则
