## 一、数据库概述

### 1.1 数据库架构

| 数据库 | 用途 | 存储引擎 |
|--------|------|----------|
| MySQL | 核心业务数据（含聊天消息 `xn_chat_log` / `xn_chat_room`） | InnoDB |
| MongoDB | 预留模型（ChatMessage/UserSession/Notification），当前聊天流未实际使用 | - |

> ⚠️ **重要**：聊天消息实际存储于 MySQL（`xn_chat_log` 表），由 `chatService` 使用 `ChatSession` / `ChatLog` 模型读写；MongoDB 的 `ChatMessage` 模型存在但当前聊天流未使用（历史结构保留）。

### 1.2 双层命名规范

本文档同时存在两层命名视角,通过 ORM 自动映射,互不冲突:

#### 1.2.1 MySQL 物理层(snake_case)

- 表名统一使用 `xn_` 前缀
- 字段名使用下划线命名法 (snake_case),如 `user_id`、`create_time`
- 索引名格式: `idx_表名_字段名`
- 主键统一使用 `id`,自增 BIGINT 类型

#### 1.2.2 API 契约层(camelCase)

- 字段名使用小驼峰命名法,如 `userId`、`nickname`、`createTime`
- 避免缩写:使用完整单词,如 `balance` 而非 `bal`
- 语义清晰:字段名应准确表达含义

### 1.3 通用字段规范

| 字段名 | 类型 | 说明 |
|--------|------|------|
| id | int/bigint | 主键ID |
| createTime | int/datetime | 创建时间 |
| updateTime | int/datetime | 更新时间 |
| status | tinyint | 状态(0/1) |

### 2.9 统一媒资表 (xn_media_asset)

存储所有上传(前端直传 COS 或本地兜底)的登记记录,用于审计留痕、定位归属、按业务级联删除文件本体。后端仅保存 URL 索引,不保存文件实体。

| 字段名 | 类型 | 说明 | 约束 |
|--------|------|------|------|
| id | BIGINT | 主键 | PK, AUTO_INCREMENT |
| user_id | BIGINT | 上传用户ID | NOT NULL |
| biz_type | VARCHAR(32) | 业务类型:circle/album/chat/avatar/feedback/misc | NOT NULL, DEFAULT 'misc' |
| biz_id | BIGINT | 关联业务ID(动态ID/相册照片ID/会话ID等) | NULL |
| url | TEXT | 文件访问地址(COS签名URL或本地/uploads路径) | NOT NULL |
| storage | VARCHAR(16) | 存储类型:cos/local | NOT NULL, DEFAULT 'cos' |
| file_type | VARCHAR(16) | 文件类型:image/audio/video/file | NOT NULL, DEFAULT 'file' |
| create_time | INT(10) | 创建时间(Unix时间戳) | NOT NULL |
| status | TINYINT(1) | 状态 0-已删除 1-正常 | DEFAULT 1 |

**biz_type 取值说明:**

| 取值 | 含义 |
|------|------|
| circle | 动态发布的图片/视频 |
| album | 相册照片 |
| chat | 聊天图片/视频/语音 |
| avatar | 用户头像 |
| feedback | 意见反馈附件 |
| misc | 其他 |

**索引设计:**

| 索引名 | 索引字段 | 索引类型 | 说明 |
|--------|---------|---------|------|
| idx_user_id | user_id | 普通索引 | 按用户查询媒资 |
| idx_biz | biz_type + biz_id | 普通索引 | 按业务类型+业务ID级联删除 |
| idx_create_time | create_time | 普通索引 | 按时间范围清理/审计 |

> 删除动态(`circleService.deletePost`)、删除相册照片、撤回聊天图片/视频/语音时,均通过 `mediaAssetService.removeByBiz(biz_type, biz_id)` 同步清理底层存储(COS/本地)与本条记录。

**建表 SQL:**

```sql
CREATE TABLE `xn_media_asset` (
  `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键',
  `user_id` BIGINT NOT NULL COMMENT '上传用户ID',
  `biz_type` VARCHAR(32) NOT NULL DEFAULT 'misc' COMMENT '业务类型 circle/album/chat/avatar/feedback/misc',
  `biz_id` BIGINT DEFAULT NULL COMMENT '关联业务ID（动态ID/相册照片ID/会话ID等）',
  `url` TEXT NOT NULL COMMENT '文件访问地址（COS签名URL或本地/uploads路径）',
  `storage` VARCHAR(16) NOT NULL DEFAULT 'cos' COMMENT '存储类型 cos/local',
  `file_type` VARCHAR(16) NOT NULL DEFAULT 'file' COMMENT '文件类型 image/audio/video/file',
  `create_time` INT(10) NOT NULL COMMENT '创建时间（Unix时间戳）',
  `status` TINYINT(1) NOT NULL DEFAULT 1 COMMENT '状态 0-已删除 1-正常',
  PRIMARY KEY (`id`),
  KEY `idx_user_id` (`user_id`),
  KEY `idx_biz` (`biz_type`, `biz_id`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='统一媒资登记表（审计/级联删除）';
```

> 该表由 Sequelize 模型 `backend/src/models/mysql/MediaAsset.js` 在 `sync({ alter: true })` 时自动创建/迁移,也可手动执行上述 SQL 初始化。

## 八、数据库优化建议

### 8.1 索引优化

1. **高频查询字段添加索引**: user_id, create_time, status
2. **唯一约束字段添加唯一索引**: mobile, open_id, order_no
3. **联合索引优化**: (user_id, status), (target_user_id, create_time)

### 8.2 分库分表建议

1. **聊天消息表**: 建议按月分表,避免数据量过大
2. **聊天记录表**: 建议定期归档到冷库（当前聊天消息存 MySQL，MongoDB 未启用，暂不建议迁移）
3. **游戏订单表**: 历史数据归档到冷库

### 8.3 缓存策略

1. **用户信息**: Redis缓存,TTL 1小时
2. **游戏分类**: Redis缓存,TTL 24小时
3. **礼物列表**: Redis缓存,TTL 12小时
4. **VIP套餐**: Redis缓存,TTL 24小时

### 8.4 数据安全

1. **敏感字段加密**: password字段使用bcrypt加密
2. **定期备份**: 每日全量备份,每小时增量备份
3. **权限控制**: 遵循最小权限原则
