## 一、系统总览

### 1.1 技术栈与运行时

| 层面 | 选型 |
|---|---|
| Web 框架 | Express（入口 `server.js`） |
| 实时通信 | Socket.IO（含 `@socket.io/redis-adapter` 横向扩展） |
| 关系库 | MySQL + Sequelize（表前缀 `xn_`，`01_init_schema.sql` 为准，无 `sequelize.sync()`） |
| 文档库 | MongoDB + Mongoose（核心数据库，用于高频写入场景；`config/mongo.js` 连接配置） |
| 缓存 | Redis（鉴权黑名单与会话吊销水位线、Socket 适配器、登录防爆破计数） |
| 音视频 | 腾讯 TRTC（UserSig 签发）+ WebRTC 备用信令 |
| 对象存储 | 腾讯云 COS（本地存储降级） |
| 大模型 | OpenAI 兼容 Chat Completions（虚拟用户/陪聊） |
| 服务端口 | 默认 `3000`，生产经 Nginx 暴露 `/api` |

### 1.2 分层结构

```
server.js                 启动、健康检查、中间件、Socket 初始化
└── src/routes/*.js       路由注册（src/routes/index.js 统一挂载 26 个模块，前缀 /api/xxx）
    └── src/controllers/  参数解析、鉴权调用、响应封装（utils/response）
        └── src/services/ 业务逻辑与事务（services/index.js 统一导出）
            └── src/models/ Sequelize 模型（MySQL）/ Mongoose 模型（Mongo）
```

- 路由加载采用 `safeRequire` 容错：单个模块加载失败不阻断启动，但会打印告警；`STRICT_ROUTES=true` 时直接终止启动。
- 未匹配的请求统一返回 `404 {code:404,message:'接口不存在'}`；未捕获异常统一返回 `500`。

### 1.3 统一响应与错误约定

所有接口统一返回 `{ code, message, data }`（`src/utils/response.js`，强制 `charset=utf-8` 防中文乱码）：

| 方法 | HTTP | 语义 |
|---|---|---|
| `success` | 200 | 成功 |
| `created` | 201 | 创建成功 |
| `badRequest` | 400 | 参数错误 |
| `unauthorized` | 401 | 未授权/令牌失效 |
| `forbidden` | 403 | 无权限/账号禁用/禁言 |
| `notFound` | 404 | 资源不存在 |
| `unprocessableEntity` | 422 | 业务逻辑错误 |
| `error` / `dbError` | 500 | 服务器/数据库错误 |

### 1.4 鉴权体系

令牌用途由 payload 的 `type` 声明（安全扫描 H-4，`config/jwt.js` 的 `TOKEN_TYPES`），校验侧按白名单接受；
没有 `type` 的历史令牌一律判为无效，签发端对未知/缺省 `type` 直接抛错。
用途之后再加一道**吊销检查**（安全扫描 H-5，`services/tokenRevocation.js`）：`auth:blacklist:<sha256(令牌)>` 单令牌拉黑 +
`auth:revoke-user|admin:<id>` 全端下线水位线，两类状态都只存 Redis；已作废 → 401「令牌已失效」，
无法确认（Redis 未连接 / 命令报错 / 超 2 秒）→ 生产 503、非生产放行（`AUTH_BLACKLIST_FAIL_MODE` 可覆盖）。

| 角色 | 中间件 | 令牌来源 | 校验要点 |
|---|---|---|---|
| C 端用户 | `authMiddleware` | `Authorization: Bearer <JWT>` | `verifyToken(token, [ACCESS])`：只认 `type=access` + 吊销检查（黑名单 + `auth:revoke-user:<id>` 水位线）+ 用户存在 + `status===1` + 未被禁言（`jinyan_time`） |
| 可选登录 | `optionalAuth` | 同上 | 同样只认 `type=access`；无令牌、用途不符、令牌无效、**已作废或无法确认**都按「未登录」放行（不填 `req.userId`，也**不回 503**——它守的是公开页面）；吊销检查排在查库之前 |
| Socket.IO 握手 | `initializeSocket` 的 `io.use` | `handshake.auth.token` / `query.token` | 只认 `type=access` + 吊销检查：已作废 → `UNAUTHORIZED`，生产无法确认 → `AUTH_SERVICE_UNAVAILABLE` |
| 管理端 | `adminAuth`（`middlewares/auth.js`） | `Authorization: Bearer` 或 `x-admin-token` | `ADMIN_TOKEN` 应急令牌（常数时间比对，不可吊销，`req.adminTokenKind='emergency'`），或 `verifyToken(token, [ADMIN])` 通过（**独立签名密钥 + `type=admin` 白名单**，安全扫描 M-3 起不再看 `role`/`role_id` 声明）**再查吊销 + 按 `adminScope` 实时回读主体**；`access`/`refresh`/`admin_refresh` 一律 403。H-5 起为 **async**，并把命中的原文留在 `req.adminToken`/`req.adminTokenKind` 供 `/logout` 使用；明确被吊销/删号 → 401，禁用 → 403「账号已被禁用」，用途不符 → 403「无管理员权限」 |
| 管理端（admin-manage） | 路由内联 `adminAuth` | `Authorization: Bearer` | 同上（同一函数，无第二套实现） |
| 细粒度权限 | `requirePermission('<模块>:<动作>')` | — | 超管或 `permissions` 含该权限点；动作仅 `read` / `write`。权限取自登录时的令牌快照，改权限需重新登录（因此**改权限本身不吊销在用令牌**，属 H-5 遗留） |
| 令牌刷新 | `POST /api/user/refresh-token` | 请求体 `refreshToken` | `refreshAccessToken` 只认 `type=refresh`，重签**前**先查吊销（已被登出或本人已全端下线 → 401；生产无法确认 → 503）；重签只结转 `userId`，其余声明不带入新令牌 |
| 登出 | `POST /api/user/logout`（`authMiddleware`）、`POST /api/admin/logout` 与 `POST /api/admin-manage/logout`（`adminAuth`） | 本次请求携带的令牌 | H-5 新增：把本次令牌写进黑名单，可选 `body.refreshToken` 需验签通过且**归属本人**才一并拉黑；C 端带 `logoutAllDevices` 改走水位线（SPA 不保存 refresh 令牌，只拉黑 access 会留一枚 30 天孤儿凭据），故**用户端登出＝全端下线** |

> ⚠️ **2026-10-05 安全扫描 H-8 起，「开发环境」列已作废**：旧实现有五个限流器挂 `skip: nodeEnv === 'development'`，而 `NODE_ENV` 缺省值正是 `development`，忘设环境变量的生产机器等于没有限流。现在六个限流器**统一不按环境豁免**，唯一开关是 `RATE_LIMIT_DISABLED=true`（生产设它后端拒绝启动），`skip = () => config.rateLimit.disabled === true`。同时：①**桶的键是 `req.ip`**，其可信度由 `config/trustProxy.js` 解析的 `TRUST_PROXY` 决定（默认 `loopback`，即只信任同机反代）——旧实现写死 `app.set('trust proxy', 1)`，直连后端者可随机化 `X-Forwarded-For` 绕过全部按 IP 计的阈值，本轮已收口；②六个限流器统一 `standardHeaders: true`（draft-6）/`legacyHeaders: false`，正常响应带 `RateLimit-*`，429 另带 `Retry-After`（此前 `apiLimiter`/`adminLoginLimiter` 之外四个只有旧 `X-RateLimit-*`）；③计数仍是进程内存（默认 MemoryStore），多实例部署每实例各算一份，属遗留（需共享 store）。本地联调被 429 拦住时用 `RATE_LIMIT_DISABLED=true` 或调大上表四个阈值键，`tests/e2e/*` 三脚本运行前必须关限流（见《部署文档》v6.10）。

## 二、实时交互能力（Socket.IO）

入口：`src/socket/index.js`，由 `server.js` 用 `initializeSocket(io)` 初始化。

### 2.1 连接与鉴权

- 令牌来源：`handshake.auth.token` 或 `handshake.query.token`。
- **严格鉴权**：无令牌 / 令牌无效 / 用户不存在一律 `next(new Error('UNAUTHORIZED'))`，不区分 Mock 模式，禁止匿名放行。H-4 起 `verifyToken(token, [TOKEN_TYPES.ACCESS])`，refresh 令牌与管理员令牌无法用于握手。
- **吊销检查（H-5）**：验签通过后调 `tokenRevocation.checkRevocation(token, decoded)`——已登出或早于「全端下线」水位线 → `UNAUTHORIZED`；状态无法确认且生产环境 fail-closed → `AUTH_SERVICE_UNAVAILABLE`（客户端按可重试处理），非生产放行并记日志。此前登出后的令牌仍可继续留在通道上收私聊与通话信令。⚠️ 该分支**无单测**（`socket/index.js` 此前无任何测试覆盖），需人工联调。
- 连接成功后：`socket.join('user:<userId>')`，写入内存在线集合 `onlineUsers`；`disconnect` 时移除。

### 2.2 房间模型

| 房间 | 用途 | 加入方式 |

| `user:<userId>` | 私聊、通话信令、P2P 定向投递 | 连接时自动 join |
| `room:<roomId>` | 房间广播（`sendToRoom` 辅助函数） | 当前代码未见显式 join，属预留能力 |

### 3.20 管理员账号与角色 `/api/admin-manage`

| 方法 | 路径 | 权限 | 说明 |

| POST | `/login` | 公开 + 防爆破 | 管理员登录（支持账号或角色账号）；与 3.19 共用 `adminLoginLimiter` 和同一个 `admin:login:fail:<账号>` 计数键，响应额外带 `refreshToken`；禁用账号 403 且不计失败次数；M-2（2026-10-05）起访问令牌默认 12h（`ADMIN_JWT_EXPIRES_IN`）并携带 `adminScope`（`account`/`role`/`emergency`，供回读判断 `id` 指向哪张表） |

**写入口径（安全扫描 M-1，2026-10-05）**：七个写接口——`POST /admins`、`PUT /admins/:id`、`PUT /admins/:id/password`、`DELETE /admins/:id`、`POST /roles`、`PUT /roles/:id`、`DELETE /roles/:id`——在 `admin:write` 之外再加**两级授权边界**（判定实现于 `utils/permissions.js` 的 `permissionsBeyondActor`/`canManageRole`/`canManageAdmin`）：①**授权边界**——向 `permissions` 写入或经角色间接生效的权限集，必须 ⊆ 操作者自身权限（越界 403「无权授予超出自身权限范围的权限: &lt;列表&gt;」）；②**对象边界**——目标管理员/角色须在操作者管辖范围内（目标为超管 id=1/role_id=1、或有效权限超出操作者、或含 `all` 一律拒绝，403「无权修改该管理员…」「无权修改该角色…」等）。超管（id=1 / role_id=1 / 权限含 `all`）不受限；`POST /admins` 始终按有效角色（缺省 2）校验，「不传 `role_id`」不再是旁路；改密/删除的边界检查先于 H-5 吊销动作，越界即 403、不改库、不发吊销。详见文末发现第 22 条。

**会话与实时权限口径（安全扫描 M-2，2026-10-05）**：`adminAuth` 此前只读令牌内声明（`role`/`role_id`/`permissions` 为登录快照）、不回查库，管理端令牌又硬编码 7 天，「改权限/换角色/禁用/删号」要等令牌过期才生效。现在：①6 处签发（`controllers/admin.js` 3 + `controllers/adminManage.js` 3）统一用 `config.jwt.adminExpiresIn`（`ADMIN_JWT_EXPIRES_IN`，默认 `12h`），payload 新增 `adminScope`（`account`/`role`/`emergency`，两张表 id 会碰撞、回读需要它判断目标表）；②`middlewares/auth.js` 新增 `resolveLiveAdmin`，`adminAuth` 在校验 `type=admin` 与吊销状态后**每次请求回读**（account → `Admin.findByPk` + 角色表 + `resolvePermissions`；role → `AdminRole.findByPk`；emergency → 仅 `ADMIN_EMERGENCY_LOGIN=true` 时有效）：已删除/旧格式（无 `adminScope`）→ 401「令牌已失效」，`status≠1` → 403「账号已被禁用」，`req.admin` 的 `role_id`/`permissions` 取库内当前值；③回读失败沿用吊销 fail 取向（生产 fail-closed 503、非生产 fail-open 按令牌快照放行并告警）。分工：改密后旧令牌收口仍**只**靠 H-5 吊销（回读不校验口令版本）；删号/禁用为「吊销 + 回读」双保险；改权限/角色不吊销令牌（避免自踢）但改库即生效。详见文末发现第 23 条。

**签名密钥与门禁口径（安全扫描 M-3，2026-10-05）**：管理端令牌此前与用户端 access/refresh 共用同一 `JWT_SECRET`，且 `adminAuth` 放行条件是「`verifyToken([ADMIN])` 通过 **且** payload 声明 `role==='admin'||role_id===1`」——后者是**可伪造的声明**，属纵深防御缺失（当前用户令牌不含该声明所以暂不可利用，一旦用户令牌带上 `role` 字段即可越权）。现在：①`config/jwt.js` 新增 `ADMIN_TYPES`/`isAdminType`/`secretForTypes`，签发与校验按**用途白名单**挑选密钥——管理端白名单用 `config.jwt.adminSecret`（`ADMIN_JWT_SECRET`，未配置时由 `HMAC-SHA256(JWT_SECRET, 'eudazi:admin-token:v1')` 派生），其余用用户端 `secret`，用错密钥的令牌在 `jwt.verify` 阶段即失败；②`adminAuth` 门禁由 `if (decoded && (role 声明))` 收紧为 `if (decoded)`——是否属于管理端只由「独立密钥 + `type=admin` 白名单」保证，主体合法性仍交给 M-2 的 `resolveLiveAdmin` 按 `adminScope` 回读（无 `adminScope` 历史令牌 → 401）；③新增 `utils/secureCompare.safeEqual`（定长 sha256 + `crypto.timingSafeEqual`），`ADMIN_TOKEN` 比对与 `controllers/adminManage.js`、`controllers/admin.js` 的环境变量应急口令比对统一改为常数时间；④`server.js` 启动自检对显式弱值 `ADMIN_JWT_SECRET` 生产拒启、对「未显式配置、密钥由 `JWT_SECRET` 派生」告警「未做泄露隔离」。**行为变更**：存量管理端令牌由用户端密钥签发，新校验下验签失败 → **403「无管理员权限」**（注意与 M-2 的 401 不同），管理员需重新登录一次。详见文末发现第 24 条。

## 四、端到端交互流程

### 4.1 登录鉴权

```
前端 POST /api/user/login (或 /login-mobile、/login-third)
  → authService 校验（bcrypt 比对 / 手机号自动注册 / 三方 openid 查询）
  → 检查 status===1、ID≥11000
  → 签发 accessToken(type=access) + refreshToken(type=refresh)（JWT，默认 7d / 30d，同一密钥）
  → 返回 { userId, accessToken, refreshToken, nickname, ... }

后续请求携带 Authorization: Bearer <accessToken>
  → authMiddleware：验签 + 用途白名单 [access]（H-4）
      → tokenRevocation.checkRevocation(decoded, token)（H-5，一次读两个键）
          auth:blacklist:<sha256(令牌原文)>      命中 → 已登出
          auth:revoke-user:<userId>              iat < 水位线 → 全端下线
          Redis 不可用/命令报错/超 2 秒 → verifiable:false
        已吊销 → 401「令牌已失效」；确认不了且 fail-closed（生产默认）→ 503
      → 查用户 → 校验 status/禁言
  → 注入 req.user / req.userId

accessToken 过期 → POST /api/user/refresh-token 用 refreshToken 换新
  → refreshAccessToken 只认 type=refresh；新令牌只结转 userId，不复制旧 payload 的其他声明
  → H-5：重签前先 checkRevocation（黑名单 + 用户水位线），已吊销的 refresh 令牌换不到新 access

登出 / 会话终止（H-5 新增）：
  POST /api/user/logout
      → 吊销当前 access（黑名单）+ 当前 refresh（黑名单，body.refreshToken 需 type=refresh 且归属本人）
      → body.logoutAllDevices 为真时再写 auth:revoke-user:<userId> 水位线 ⇒ 该账号此前签发的全部令牌（含 30 天 refresh）一次作废
      → C 端 SPA 不保存 refreshToken，前端 authService.logout() 固定带 logoutAllDevices:true，故产品口径为「登出即全端下线」
  POST /api/user/reset-password
      → 改库**前**写 auth:revoke-user:<id> 水位线（不打黑名单，旧 access 靠 iat 判死）
      → 生产吊销确认不了 → 503 且**不**改密；非生产 fail-open → 改密成功并回 devicesRevoked:false
```

> H-4 的行为变更：升级前签发的令牌没有 `type`，`authMiddleware`/`adminAuth`/Socket 握手一律判无效 →
> C 端与管理端都会走到 401/403 分支（前端清本地登录态并跳登录页），即**上线后全端重新登录**。
>
> H-5 的行为变更：吊销状态**只在 Redis**，且读侧检查覆盖了 `authMiddleware` / `optionalAuth` / `adminAuth` / Socket 握手四个入口。
> 后果是 `AUTH_BLACKLIST_FAIL_MODE` 变成承重配置——生产环境 Redis 抖动或实例不可达时，所有需要鉴权的流量会返回 503（H-5 之前是跳过检查直接放行）。
>
> M-2 的行为变更（2026-10-05）：存量管理员令牌不带 `adminScope`，`adminAuth` 一律 401「令牌已失效」→ **管理员需重新登录一次**（与 H-4 全端重登同口径，C 端不受影响）；此后改权限/换角色/禁用/删号不再有最长 7 天的生效窗口，下一个请求即按数据库当前值判定。
>
> M-3 的行为变更（2026-10-05）：管理端令牌改用独立签名密钥（`ADMIN_JWT_SECRET`，未配置则由 `JWT_SECRET` 派生），存量管理员令牌由**用户端密钥**签发、新校验验签失败 → **403「无管理员权限」**（连合法管理端令牌这一关都没过）→ **管理员需重新登录一次**；`adminAuth` 不再采信 `role`/`role_id` 声明（改由「独立密钥 + `type=admin` 白名单」保证），`ADMIN_TOKEN` 与两处环境变量应急口令比对改为常数时间。

管理端登录（`/api/admin/login`、`/api/admin-manage/login`，安全扫描 H-3 后的口径）：

```
POST {username, password}
  → adminLoginLimiter：单 IP 15 分钟 5 次（不豁免开发环境），超了 429
  → adminLoginGuard.getLoginLockState(账号归一化小写)
      Redis 不可用 / 命令报错 / 超 2 秒 → verifiable:false → 503 保守拒绝
      已锁 → 429 + data.retryAfterSec
  → 口令三级：xn_admin(status=1, bcrypt) → xn_admin_role 自带口令 → ADMIN_EMERGENCY_LOGIN 环境变量账号(safeEqual)
      命中任一 → clearLoginFailures → 签发管理员 JWT type=admin（M-2 起默认 12h + adminScope；/admin-manage/login 另带 type=admin_refresh，当前无消费方）
      全部未命中 → recordLoginFailure（不存在的用户名同样计数）→ 统一 401「用户名或密码错误」
  → 参数缺失 → 400，不计失败（防空请求锁死管理员账号）
```

管理端会话终止（H-5 新增；M-2 起叠加实时回读）：

```
adminAuth（异步）：验签 + 白名单 [admin] → checkRevocation（黑名单 + auth:revoke-admin:<id> 水位线）
  → req.adminToken / req.adminTokenKind（'jwt' | 'emergency'）
  → 已吊销 401；确认不了且 fail-closed 503；用途不符/格式非法 403
  → M-2 实时回读（resolveLiveAdmin，按 adminScope 查库）：
      account → Admin.findByPk + (role_id ? AdminRole.findByPk) + resolvePermissions
      role    → AdminRole.findByPk
      emergency → 仅 ADMIN_EMERGENCY_LOGIN 仍开启时有效
      已删除 / 旧格式(无 adminScope) → 401「令牌已失效」；status≠1 → 403「账号已被禁用」
      正常 → req.admin 的 role_id/permissions 用库内当前值覆盖令牌快照
      回读抛错 → 生产 fail-closed 503；非生产按令牌快照放行并告警

POST /api/admin/logout | /api/admin-manage/logout（同一实现）
  → 吊销 req.adminToken（本次真正命中的那一枚）+ 可选 body.refreshToken（需 type=admin_refresh 且归属本人）
  → emergency 令牌（ADMIN_TOKEN）revocable:false：签发不带 jti、按环境变量比对，无从吊销 → 只能改环境变量（遗留）
  → fail-open/closed 与 C 端登出同口径

PUT /api/admin-manage/admins/:id/password、DELETE /admins/:id、PUT /admins/:id(status≠1)
  → 改库前 revokeAllAdminTokens(id) 写水位线
  → M-2 分工：改密后旧令牌仍只靠吊销（回读不校验口令版本）；删号/禁用另有第二道——实时回读本身就能拦（401/403），非生产吊销 fail-open 失败时也不留空窗
```
