# 后端交互功能梳理

> 本文档基于当前代码（`backend/`）静态阅读整理，覆盖三类内容：**实时交互能力（Socket.IO）**、**全部 REST 接口清单（按模块）**、**端到端交互流程（前端 → 后端 → 落库）**。
> 文末附「代码核对发现」章节，列出静态阅读中发现的字段/逻辑不一致，供后续核对，不代表运行时一定出错。
> 整理范围：`src/routes`、`src/controllers`、`src/services`、`src/socket`、`src/middlewares`、`server.js`。

---

## 一、系统总览

### 1.1 技术栈与运行时

| 层面 | 选型 |
|---|---|
| Web 框架 | Express（入口 `server.js`） |
| 实时通信 | Socket.IO（含 `@socket.io/redis-adapter` 横向扩展） |
| 关系库 | MySQL + Sequelize（表前缀 `xn_`，`init_schema.sql` 为准，无 `sequelize.sync()`） |
| 文档库 | MongoDB（`ChatMessage` / `Notification` / `UserSession`，即 `src/models/mongo`） |
| 缓存 | Redis（鉴权黑名单、Socket 适配器） |
| 音视频 | 腾讯 TRTC（UserSig 签发）+ WebRTC 备用信令 |
| 对象存储 | 腾讯云 COS（本地存储降级） |
| 大模型 | OpenAI 兼容 Chat Completions（虚拟用户/陪聊） |
| 服务端口 | 默认 `3000`，生产经 Nginx 暴露 `/api` |

### 1.2 分层结构

```
server.js                 启动、健康检查、中间件、Socket 初始化
└── src/routes/*.js       路由注册（src/routes/index.js 统一挂载 26 个模块，前缀 /api/xxx）
    └── src/controllers/  参数解析、鉴权调用、响应封装（utils/response）
        └── src/services/ 业务逻辑与事务（services/index.js 统一导出）
            └── src/models/ Sequelize 模型（MySQL）/ Mongoose 模型（Mongo）
```

- 路由加载采用 `safeRequire` 容错：单个模块加载失败不阻断启动，但会打印告警；`STRICT_ROUTES=true` 时直接终止启动。
- 未匹配的请求统一返回 `404 {code:404,message:'接口不存在'}`；未捕获异常统一返回 `500`。

### 1.3 统一响应与错误约定

所有接口统一返回 `{ code, message, data }`（`src/utils/response.js`，强制 `charset=utf-8` 防中文乱码）：

| 方法 | HTTP | 语义 |
|---|---|---|
| `success` | 200 | 成功 |
| `created` | 201 | 创建成功 |
| `badRequest` | 400 | 参数错误 |
| `unauthorized` | 401 | 未授权/令牌失效 |
| `forbidden` | 403 | 无权限/账号禁用/禁言 |
| `notFound` | 404 | 资源不存在 |
| `unprocessableEntity` | 422 | 业务逻辑错误 |
| `error` / `dbError` | 500 | 服务器/数据库错误 |

### 1.4 鉴权体系

| 角色 | 中间件 | 令牌来源 | 校验要点 |
|---|---|---|---|
| C 端用户 | `authMiddleware` | `Authorization: Bearer <JWT>` | JWT 有效 + Redis 黑名单 + 用户存在 + `status===1` + 未被禁言（`jinyan_time`） |
| 可选登录 | `optionalAuth` | 同上 | 无令牌也放行，仅尽量填充 `req.user` |
| 管理端 | `adminAuth`（`middlewares/auth.js`） | `Authorization: Bearer` 或 `x-admin-token` | `ADMIN_TOKEN` 应急令牌，或 JWT 声明 `role==='admin'` / `role_id===1` |
| 管理端（admin-manage） | 路由内联 `adminAuth` | `Authorization: Bearer` | JWT 含 `roleId` / `role==='admin'` / `role_id===1` |
| 细粒度权限 | `requirePermission('<模块>:<动作>')` | — | 超管或 `permissions` 含该权限点；动作仅 `read` / `write` |

### 1.5 限流策略（`src/middlewares/rateLimit.js`，开发环境跳过）

| 限流器 | 窗口 | 上限 | 应用点 |
|---|---|---|---|
| `loginLimiter` | 15 分钟 | 100 次 | 登录/注册/重置密码/手机号登录/三方登录 |
| `smsLimiter` | 60 秒 | 1 次 | 发送短信验证码 |
| `uploadLimiter` | 60 秒 | 20 次 | 上传接口 |
| `apiLimiter` | 60 秒 | 100 次（可配） | 全局 API（已定义并导出，但**当前代码未见挂载**） |

## 二、实时交互能力（Socket.IO）

入口：`src/socket/index.js`，由 `server.js` 用 `initializeSocket(io)` 初始化。

### 2.1 连接与鉴权

- 令牌来源：`handshake.auth.token` 或 `handshake.query.token`。
- **严格鉴权**：无令牌 / 令牌无效 / 用户不存在一律 `next(new Error('UNAUTHORIZED'))`，不区分 Mock 模式，禁止匿名放行。
- 连接成功后：`socket.join('user:<userId>')`，写入内存在线集合 `onlineUsers`；`disconnect` 时移除。

### 2.2 房间模型

| 房间 | 用途 | 加入方式 |
|---|---|---|
| `user:<userId>` | 私聊、通话信令、P2P 定向投递 | 连接时自动 join |
| `room:<roomId>` | 房间广播（`sendToRoom` 辅助函数） | 当前代码未见显式 join，属预留能力 |

### 2.3 客户端 → 服务端事件

| 事件 | 载荷 | 说明 |
|---|---|---|
| `private_message` | `{toId, content, type, mediaUrl, duration}` | 发送私聊；复用 `chatService.sendMessage` 落库后再转发 |
| `call_invite` | `{toId, callType, trtcRoomId, callId, useWebRTC}` | 通话邀请（TRTC 或 WebRTC） |
| `call_cancel` | `{toId}` | 主叫取消 |
| `call_accept` | `{toId, trtcRoomId}` | 被叫接听 |
| `call_reject` | `{toId}` | 被叫拒绝 |
| `call_end` | `{toId, duration}` | 结束通话 |
| `webrtc_offer` | `{toId, sdp}` | WebRTC 信令 |
| `webrtc_answer` | `{toId, sdp}` | WebRTC 信令 |
| `webrtc_ice_candidate` | `{toId, candidate}` | WebRTC ICE |
| `typing` | `{toId}` | 正在输入 |
| `revoke_message` | `{toId, messageId}` | 撤回消息（仅转发，落库走 REST `/api/chat/revoke`） |
| `p2p_fetch_request` | `{toId, requestId, url, type}` | P2P 内容取回请求（头像/缩略图） |
| `p2p_fetch_response` | `{toId, requestId, payload, fallbackUrl}` | P2P 取回响应（DataChannel 字节或签名 URL 回退） |
| `p2p_offer` / `p2p_answer` / `p2p_ice_candidate` | `{toId, requestId, ...}` | P2P DataChannel 建连信令 |

### 2.4 服务端 → 客户端事件

| 事件 | 说明 |
|---|---|
| `private_message` | 投递给接收方 `user:<toId>` |
| `private_message_ack` | 回执给发送方 `{id, sendTime}` |
| `call_invite` / `call_cancel` / `call_reject` / `call_accept` / `call_end` | 通话状态流转转发 |
| `webrtc_offer` / `webrtc_answer` / `webrtc_ice_candidate` | WebRTC 信令转发 |
| `typing` | 输入状态转发 |
| `message_revoked` | 撤回通知 `{messageId, fromId}` |
| `p2p_fetch_request` / `p2p_fetch_response` / `p2p_offer` / `p2p_answer` / `p2p_ice_candidate` | P2P 取数与建连转发 |
| `error` | 服务端处理异常时回传 `{message}` |

### 2.5 导出辅助函数

| 函数 | 作用 |
|---|---|
| `sendToUser(userId, event, data)` | 定向推送 `user:<id>` |
| `sendToRoom(roomId, event, data)` | 房间广播（预留） |
| `sendToAll(event, data)` | 全局广播 |
| `isUserOnline(userId)` | 在线状态查询（供 `GET /api/p2p/peer-online` 使用） |
| `getIO()` | 获取 io 实例 |

### 2.6 横向扩展

- `setupRedisAdapter` 使用 `@socket.io/redis-adapter`，让私聊/通话/房间广播跨副本同步。
- Redis 不可用时防御式降级为内存 adapter（单实例），不阻断服务；Mock 模式直接跳过。

## 四、端到端交互流程

### 4.1 登录鉴权

```
前端 POST /api/user/login (或 /login-mobile、/login-third)
  → authService 校验（bcrypt 比对 / 手机号自动注册 / 三方 openid 查询）
  → 检查 status===1、ID≥11000
  → 签发 accessToken + refreshToken（JWT，默认 7d / 30d）
  → 返回 { userId, accessToken, refreshToken, nickname, ... }

后续请求携带 Authorization: Bearer <accessToken>
  → authMiddleware：验签 → Redis 黑名单查询（2s 兜底）→ 查用户 → 校验 status/禁言
  → 注入 req.user / req.userId

accessToken 过期 → POST /api/user/refresh-token 用 refreshToken 换新
```

### 4.2 私聊消息（实时 + 落库）

```
发送方 Socket emit 'private_message' {toId, content, type, mediaUrl, duration}
  → socket.on('private_message')
    → chatService.sendMessage(fromId, toId, ...)
        1) 查发送方（status!==1 抛"已被禁言"）、查对端（优先 VirtualUser，兼容 User）
        2) 写 xn_chat_log（isread=0, is_del=0, is_revoked=0）
        3) 媒体消息（type 2/3/5）登记 xn_media_asset
        4) upsert 双方 xn_chat_room 会话（发送方 unread 不变；接收方 unread_count+1）
    → io.to(`user:<toId>`).emit('private_message', messageData)
    → socket.emit('private_message_ack', {id, sendTime})

REST 兜底：POST /api/chat/send 走同一 chatService.sendMessage
已读：POST /api/chat/mark-read → 更新 xn_chat_log.isread=1 + 会话 unread_count=0
撤回：POST /api/chat/revoke（限 2 分钟内、本人）→ is_revoked=1 + 清理媒资；Socket emit 'message_revoked' 通知对端
```

### 4.3 音视频通话（信令 + 计费）

```
1) 主叫 POST /api/trtc/start → CallBilling 侧写 xn_call_record（status=0，生成 trtc_room_id）
2) 主叫 Socket emit 'call_invite' → 转发给 user:<calleeId>
3) 被叫 Socket emit 'call_accept' → 主叫侧；同时 POST /api/trtc/accept（status 0→1，记 connect_time）
   或 'call_reject' / POST /api/trtc/reject（status 0→2）
4) 通话中：TRTC UserSig（GET /api/trtc/auth）或 WebRTC 信令（offer/answer/ice 转发）
5) 结束：Socket emit 'call_end' + POST /api/trtc/end
     → status 1→4，duration = now - connect_time
     → 若 is_companion_call===1 且 duration>0 → createBilling()
         · 180s 免费，之后按 60s 取整计费，单价 1 元/分钟
         · 被叫抽成 70%（入 gift_money），主叫扣 money
         · 主叫余额不足则结束通话并抛错
6) P2P 取数：GET /api/p2p/peer-online 探测可达性；随后 p2p_fetch_request/response + DataChannel 信令
```

### 4.4 礼物 / 红包资金流

```
送礼 POST /api/gift/send {receiverId, giftId}
  → 事务：扣送礼人 money；收款人 +70%（money + gift_money + gift_money_zong 三处同增）；写 xn_gift_log
  → 返回礼物动画信息（SVGA）

红包发放 POST /api/gift/redpacket/send → 事务扣 money + 写 xn_red_packet（24h 过期）
红包领取 POST /api/gift/redpacket/receive
  → 校验未过期/非本人/未领过；拼手气随机或普通均分
  → 事务：写 xn_red_packet_log + 加余额 + 递减余量（领完置 status=1）

提现（礼物）POST /api/gift/withdraw → 校验 ≥100 且 gift_money 足够，算手续费，写 xn_withdraw(待审)
管理审批 POST /api/gift/admin/withdraw/approve → 扣 gift_money，置 is_check=1
```

### 4.5 充值（微信支付 / 密卡 / 密钥）

```
套餐列表 GET /api/pay/packages
下单     POST /api/pay/create-order → 写 xn_order_chong(status=0)
微信支付 POST /api/pay/wx-order → 拉起支付
支付回调 POST /api/pay/wx-notify（公开）→ payService.wxPayCallback
     → 事务：订单置 status=1 + 加 User.money（含赠送金币）
密卡     POST /api/pay/validate-card（校验）→ POST /api/pay/use-card（事务：卡置已用 + 加余额）
密钥     POST /api/pay/redeem-key（25 位，事务：卡置已用 + 加余额）
```

### 4.6 陪玩订单

```
下单 POST /api/games/push → 事务创建 xn_game_order + 扣买家 money（status=0 待接单）
抢单 POST /api/games/grab → 陪玩师接单（status→1）
开始 POST /api/games/start → status→2 进行中
完成 POST /api/games/complete → status→3 已完成
取消 POST /api/games/cancel → 事务全额退款（status=4）
评价 POST /api/games/evaluate
陪玩师入驻 POST /api/games/apply → 管理端 /api/admin/companion-applications/:id/approve 审核
```

### 4.7 私密帖解锁（含扣费）

```
查看详情 GET /api/circle/post/:id
  → 非本人、is_private∈(1,2) 且无解锁记录 → 返回 { locked:true, privateType, privatePrice }，不下发内容
解锁 POST /api/circle/unlock {postId, password?}
  → is_private=1（密码帖）：比对 md5(password)
  → is_private=2（付费帖）：扣买家 money → 加作者 money → 写 xn_post_unlock
```

### 4.8 虚拟用户 AI 陪聊

```
POST /api/virtual-user/:id/chat {message}
  → 校验虚拟用户 status===1 且 online_status===1
  → 1) 先落库用户消息 xn_virtual_chat_history
  → 2) 取最近 N 条（LLM_MAX_CONTEXT_MESSAGES）拼接上下文 → llmService.generateReply
       · 未配置 LLM 或失败 → 规则回复 generateAiReply 降级
  → 3) 事务写 AI 回复 + 裁剪超限历史（默认 200 条）
       · 写入失败 → 补偿删除孤立的用户消息
虚拟用户在线状态由 virtualUserOnlineScheduler 定时调度（随机在线时段/时长）
```

## 六、代码核对发现（建议复核）

以下为静态阅读中发现的字段名/逻辑不一致或降级实现，**建议结合 `sql/init_schema.sql` 与实际运行核对**，本文档仅如实记录代码现状：

1. **聊天对端以虚拟用户为主**：`chatService` 的会话/对端查询优先走 `xn_virtual_user`，真实用户仅为兜底，即"私聊"当前主要面向虚拟用户；`ChatSession` 外键字段为 `virtual_user_id`。
2. **礼物流水字段口径不一致** —— ✅ 已于 2026-10-01 修复：`walletService` 收入聚合改用真实列 `xn_gift_log.user_id`（收款人）/ `totalmoney`。
3. **通话计费字段口径不一致** —— ✅ 已于 2026-10-01 修复：`walletService` 改查 `b.total_amount` / `b.call_id` / `r.call_type`；`callBillingService.createBilling` 计费单改为 `status=1` + `settle_time`（通话结束即时结算），并去掉余额不足时对 `endCall` 的递归调用。
4. **TRTC 计费接口为模拟实现**：`trtcService.startBilling/endBilling` 使用随机时长与固定单价返回，未落库（真实计费在 `callBillingService`）。
5. **陪玩订单完成不分账** —— ✅ 已于 2026-10-01 修复：`completeOrder` 事务内按系统设置比例（`order_commission_rate`，默认 70%）给陪玩师分账并累加 `xn_companion_profile` 收入/单量；`evaluateOrder` 回写滚动平均分与评价数（`pingjia_status` 防重复评价）；钱包订单收入/支出查询一并修正。
6. **预约无真实资金流** —— ✅ 已于 2026-10-01 修复：按**收费预约**实现——`createReserve` 下单原子扣款（含时段占用事务）、`cancelReserve` 按 `>=24h 全退 / >=12h 退 50% / 否则不退` 退款、`completeReserve` 完成结算给陪玩师。同时修正了 `Reserve` 模型与建表脚本的列对齐（`duration/price/remark/service_type`），存量库需执行增量 SQL 补列。
7. **相册未落库** —— ✅ 已于 2026-10-01 修复：`albumService` 改用 `AlbumPhoto` 持久化，新增 `xn_album_like` 支持点赞去重与"我是否点过赞"。
8. **需求大厅无撮合**：`demandService` 模型注释的 matched/completed 状态代码从不设置，实际仅 active/cancelled，budget 不冻结。（批次3未处理，待定）
9. **`notice` / `search/hot` 为硬编码** —— 已于 2026-10-01 在代码注释中标注为占位数据（未落库，按既定决策保持硬编码）。
10. **`tagService` 部分能力降级** —— ✅ 已于 2026-10-01 修复：`xn_virtual_user_tag` 增加 `category`/`is_default`、`xn_virtual_user_tag_relation` 增加 `is_primary`；`getTagsByCategory`/`getDefaultTags`/`setPrimaryTag` 均为真实过滤与写入。
11. **管理端权限口径** —— ✅ 已于 2026-10-01 修复：`resolvePermissions` 不再"无角色空权限兜底 `['all']`"，改为返回空权限（仅 `is_super`/超管给全权限）；`adminLogin` 的环境变量应急登录改为需显式 `ADMIN_EMERGENCY_LOGIN=true`；`routes/adminManage.js` 内联 `adminAuth` 已删除，统一复用 `middlewares/auth.js` 的实现。
12. **全局限流未挂载** —— ✅ 已于 2026-10-01 修复：`server.js` 已在业务路由前 `app.use('/api', apiLimiter)`（健康检查/测试路由不受影响，开发环境自动跳过）。生产阈值需按流量上调（见 `.env.production.example` 的 `RATE_LIMIT_*`）。
