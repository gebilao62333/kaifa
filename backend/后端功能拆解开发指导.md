**充值入账唯一口径（安全扫描 H-2，v6.12）**：两条支付链路（`/wx-notify` 渠道回调、`/wx-callback` 客户端回执）都收敛到 `payService.settleRechargeOrder(order, verification)`，它按三步走：

1. `verification.verified === true` 才继续，否则抛 `PAY_ORDER_UNVERIFIED`（403）；实付分值 `paidCents` 存在时必须等于 `round(order.amount × 100)`，不一致抛 `PAY_ORDER_AMOUNT_MISMATCH`（422）——金币数量只从 `xn_order_chong.coins` 取，渠道金额从参与计算、只参与核对。
2. 同一事务内 `OrderChong.update({ status:1, pay_time, update_time }, { where: { id, status:0 } })`，影响行数为 0 即抛 `PAY_ORDER_ALREADY_SETTLED`。这一步替换了原「`findOne({status:0})` → `instance.update` → `User.increment`」的查后改：微信会对同一订单并发重发通知，两个请求都能读到未支付状态，于是一单加两次币。
3. 抢到状态迁移的那个请求才 `User.increment('money')`，加币与置状态同事务提交。

`wxPayCallback` 只负责「按 `order_no` 取单 + 校验 `user_id` 归属（非本人 403 / 不存在 404）」后委派给它；`/wx-query`、`/wx-close` 复用 `requireOwnedOrder(userId, orderNo)`。错误码→HTTP 的分流见《后端API接口文档》5.9。

**遗留**：`xn_order_chong` 没有支付流水号列，平台 `transaction_id` 只进日志；支付宝无服务端下单/回调实现。

### 2.10 管理员后台模块 (Admin)

**路由前缀**: `/api/admin`
**文件**: `routes/admin.js` → `controllers/admin.js`

除 `/login` 外，全部接口需 `adminAuth` + `requirePermission('资源:read|write')` 双重校验。共 104 个接口，按业务分组如下：

**登录**

| 接口 | 方法 | 认证 | 说明 |
|------|------|------|------|
| `/login` | POST | `adminLoginLimiter` + 账号锁定 | 管理员登录（单 IP 15 分钟 5 次；两个入口共用 Redis `admin:login:fail:<归一化账号>` 计数，连续失败 5 次锁 15 分钟，安全扫描 H-3） |
| `/logout` | POST | `adminAuth` | **服务端登出（安全扫描 H-5，v6.15 新增）**：两个前缀各挂一个入口、同一实现。吊销 `req.adminToken`（本次真正通过校验的那一枚，因为 `adminAuth` 同时接受 `Authorization` 与 `x-admin-token`），可选 `body.refreshToken` 需 `type=admin_refresh` 且 `id` 归属本人；`ADMIN_TOKEN` 应急固定令牌走 `revocable:false` 分支，只清前端本地态 |

**登录口径（安全扫描 H-3，v6.13）**：`/api/admin/login` 与 `/api/admin-manage/login` 是同一份后台口令的两个入口，共用一套防护——
①`adminLoginLimiter` 单 IP 15 分钟 5 次（`ADMIN_LOGIN_RATE_LIMIT_MAX`，不豁免开发环境）；
②`services/adminLoginGuard.js` 按账号计数（Redis `admin:login:fail:<trim+lowercase 后的账号>`，15 分钟内失败 5 次即锁，成功登录清零），
不存在的用户名同样计数（否则锁定行为本身成了账号存在性 oracle），缺参数的 400 **不计数**（否则任何人可用空请求把管理员锁在门外）；
③Redis 不可用/超时 → `verifiable:false` → **503 保守拒绝**，口令校验不因缓存抖动降级。
口令来源三级：`xn_admin`（`status=1`）→ `xn_admin_role` 自带口令 → `ADMIN_EMERGENCY_LOGIN=true` 的环境变量账号；三者都不过统一 401，文案不区分账号是否存在。

**会话终止与实时权限口径（安全扫描 H-5，v6.15；M-2，v6.21 改造）**：M-2 之前 `adminAuth` **只验令牌、不回查 `xn_admin`**，`role`/`role_id`/`permissions` 都是登录时的快照，所以「改口令 / 禁用 / 删除管理员」这三类改库动作本身踢不掉已经到手的会话。现在两道防线：
①**吊销水位线（H-5）**——「改口令 / 禁用 / 删除管理员」在改库**之前**先写水位线
`auth:revoke-admin:<id>`（值 `now+1` 秒，TTL `JWT_REFRESH_EXPIRES_IN`；`iat` 早于它的令牌一律作废），
顺序不能反——生产环境确认不了吊销就不改库并回 503，否则就是「密码已换、旧令牌照常能用」或「查无此人但仍可操作」；
②**实时回读（M-2）**——`adminAuth` 每次请求按令牌的 `adminScope` 回读主体（`account` → `xn_admin` + 角色表；`role` → `xn_admin_role`；`emergency` → 仅 `ADMIN_EMERGENCY_LOGIN=true` 时有效）：已删除 → 401「令牌已失效」，`status≠1` → 403「账号已被禁用」，`permissions`/`role_id` 一律取库内当前值——**改权限 / 换角色 / 禁用 / 删号在下一个请求立即生效**；回读失败沿用 fail 取向（生产 503、非生产按令牌快照放行并告警）。
分工：改口令后旧令牌仍**只**靠①（回读不校验口令版本，`updateAdminPassword` 的吊销不能省）；删号/禁用为①+②双保险；
`updateAdmin` 改 `permissions`/`role_id` **不**吊销令牌（避免管理员改自己权限时把自己踢下线），但改库即生效、无需重登（M-1 时「需被改者重新登录」的口径已被 M-2 覆盖）。
令牌时效：管理端访问令牌独立为 `ADMIN_JWT_EXPIRES_IN`（默认 12h）；无 `adminScope` 的存量令牌一律 401、需重新登录一次。
用户侧封号（`/users/:id/status`）是**尽力而为**：`authMiddleware` 每请求回查 `xn_user.status`，封号本身已生效，吊销失败只记日志。

**写入口径（安全扫描 M-1，v6.20）**：七个写接口（`/admins` POST、`/admins/:id` PUT/DELETE、`/admins/:id/password` PUT、`/roles` POST、`/roles/:id` PUT/DELETE）在 `admin:write` 之上再加两级边界——非超管不能操作超管（`id=1`/`role_id=1`/`is_super`）及「有效权限超出自身范围」的对象（403：「无权修改该管理员：目标账号权限超出你的管理范围」「无权修改该管理员密码：…」「无权删除该管理员：…」「无权修改该角色：超出自身权限范围」「无权删除该角色：超出自身权限范围」），提交的 `permissions`/`role_id` 也必须 ⊆ 自身权限（403：「无权授予超出自身权限范围的权限: <列表>」「无权分配超出自身权限范围的角色」）；判定实现于 `utils/permissions.js` 的 `permissionsBeyondActor`/`canManageRole`/`canManageAdmin`，超管（id=1 / role_id=1 / 权限含 `all`）不受限。`POST /admins` 始终按有效角色（缺省 2）校验，不传 `role_id` 不再是旁路。改密/删除的边界检查先于 H-5 吊销动作，越界即 403 不改库、不发吊销。M-2（v6.21）起 `adminAuth` 每请求实时回读，这里改掉的 `permissions`/`role_id`/`status` 与被判定者的「自身权限」都在**下一个请求**即取库内当前值（改权限/角色不吊销令牌、无需重登；禁用则直接 403）。

### 2.19 音视频通话模块 (TRTC)

**路由前缀**: `/api/trtc`
**文件**: `routes/trtc.js` → `controllers/trtc.js` → `services/trtcService.js` / `services/callBillingService.js`

| 接口 | 方法 | 认证 | 说明 |
|------|------|------|------|
| `/auth` | GET | JWT | 获取 TRTC 进房票据 (UserSig)。**必须带 `?roomId=`** 才发票，服务端先核对请求者是该通话的主/被叫（安全扫描 C-4，见下方「房间权限口径」）；不带 `roomId` 只回「通道是否开通」 |
| `/start` | POST | JWT | 发起通话 (caller → callee)，同时用 `crypto.randomInt` + 进行中通话查重分配 `trtcRoomId` |
| `/cancel` | POST | JWT | 取消通话 (超时/主动取消) |
| `/reject` | POST | JWT | 拒绝通话 |
| `/accept` | POST | JWT | 接通通话 |
| `/end` | POST | JWT | 结束通话 |
| `/history` | GET | JWT | 获取通话记录 |
| `/room/create` | POST | JWT | 创建音视频房间（**占位实现**：返回随机对象、从不落库，前端无调用方） |
| `/room/enter` | POST | JWT | 进入房间（需为该通话双方之一且 `status ∈ {0,1}`） |
| `/room/leave` | POST | JWT | 离开房间（需为该通话双方之一；通话已结束仍允许，保证挂断后能干净退房） |
| `/room/:roomId` | GET | JWT | 获取房间信息（需为该通话双方之一，返回真实状态；此前不收 userId 且写死 `status:'active'`） |
| `/billing/start` | POST | JWT | 开始计费（同样受房间闸门约束；**占位实现**，不落库） |
| `/billing/end` | POST | JWT | 结束计费并结算（**占位实现**：返回随机时长与费用） |

**通话流程**:
```
caller发起(start) → callee收到通知 → accept/reject → 通话中 → end
                                    → timeout → cancel
```

**房间权限口径（安全扫描 C-4 收口）**：项目没有「房间表」，房间成员的唯一真相来源是
`xn_call_record` 的 `trtc_room_id` + `caller_id` + `callee_id`。`trtcService.resolveRoomCall(userId, roomId)`
按 `ORDER BY status ASC, create_time DESC` 取单（优先命中仍在进行的通话，兼容存量重复号），
校验请求者是双方之一；`requireEnterableRoom` 再要求 `status ∈ {0 呼叫中, 1 已接通}`。
接入点：`getAuth`（带 roomId）、`enterRoom`、`leaveRoom`（只查身份）、`getRoomInfo`、`startBilling`。
错误分流：400 房间号为空 / 403 非成员 / 404 房间不存在 / 422 通话已结束或房间号非法 / 500 意外故障（不伪装成业务拒绝）。
房间号分配：`callBillingService.allocateTrtcRoomId()` = `crypto.randomInt(1, 1000000)` + 对进行中通话查重，最多重试 5 次。
**遗留**：①票据仍是房间无关的普通 UserSig，没有用腾讯 PrivateMapKey 绑房（现有 `generateRoomSig` 是**字符串房间号** userbuf 布局，前端进数字房间，离线不可验证）；
②`room/create` 与 `billing/*` 仍不落库；③socket 的 `call_*`/`webrtc_*` 转发仍信任客户端上报的 `toId`。

**计费**: 仅 `is_companion_call=1` 的陪伴通话在 `endCall` 时结算：免费 180 秒，超出部分按 60 秒向上取整，
单价 1 金币/分钟，陪玩分账 0.7（记入 `gift_money`）；`total_amount<=0` 不建单。
主叫 `money` 走条件扣减（`WHERE money >= total`）+ 影响行数判定，扣不动即整单回滚报「余额不足，通话已结束」。

**相关表**: `xn_call_record`, `xn_call_billing`

### 2.30 中间件

**目录**: `backend/src/middlewares/`（6 个文件）

| 文件 | 导出 | 说明 |
|------|------|------|
| `auth.js` | `authMiddleware` / `optionalAuth` / `adminAuth` / `resolveLiveAdmin` | JWT 校验（提取 `req.user`/`req.userId`）、可选认证、管理员身份校验。安全扫描 H-4 起三个入口都带**令牌用途白名单**：前两者只接受 `type=access`，`adminAuth` 只接受 `type=admin`（或 `ADMIN_TOKEN` 固定应急令牌），用途不符即按验签失败处理（401/403）。安全扫描 H-5 起三个入口再查**吊销状态**（`services/tokenRevocation.js`）：已作废 → 401「令牌已失效」；无法确认（Redis 未连接/命令报错/超 2 秒）→ 生产 503、非生产放行，`optionalAuth` 则一律按匿名处理而不是 503。`adminAuth` 因此**改为 async**，并把命中的那一枚原文留在 `req.adminToken`/`req.adminTokenKind`（`jwt` 或 `emergency`）供 `/logout` 使用。安全扫描 M-2（v6.21）起，`adminAuth` 在吊销检查之后还按 payload 的 `adminScope` **实时回读数据库主体**（`resolveLiveAdmin`：`account` → `Admin.findByPk` + 角色表；`role` → `AdminRole.findByPk`；`emergency` → 仅 `ADMIN_EMERGENCY_LOGIN=true` 时有效）——已删除/旧格式令牌（无 `adminScope`）→ 401「令牌已失效」，`status≠1` → 403「账号已被禁用」，`req.admin` 的 `role_id`/`permissions` 用库内当前值覆盖令牌快照；回读失败沿用 fail 取向（生产 fail-closed 503，非生产按令牌快照放行并告警）。管理端令牌时效相应独立为 `ADMIN_JWT_EXPIRES_IN`（默认 12h，签发侧 `config.jwt.adminExpiresIn`） |
| `services/tokenRevocation.js` | `revokeToken` / `revokeAllUserTokens` / `revokeAllAdminTokens` / `checkRevocation` / `revocationFailMode` | **安全扫描 H-5 新增**，吊销状态唯一读写入口。两类状态都只存 Redis：`auth:blacklist:<sha256(令牌)>`（单令牌拉黑，TTL=剩余寿命）与 `auth:revoke-user:<id>`/`auth:revoke-admin:<id>`（水位线，`iat` 早于它即作废，TTL=`JWT_REFRESH_EXPIRES_IN`）。Redis 读写用 `withRedisTimeout` 包 2 秒并把结果裹成 `{ value }`，以区分「键不存在（可确认未吊销）」与「命令报错/超时（不可确认）」；只登记 `verifyToken` 通过的令牌 |
| `permission.js` | `requirePermission` | RBAC 权限点校验（如 `user:read`、`withdraw:write`） |
| `rateLimit.js` | `apiLimiter` / `loginLimiter` / `adminLoginLimiter` / `smsLimiter` / `cardLimiter` / `uploadLimiter` | 基于 express-rate-limit 的全局限流（默认 100 次/60 秒，`RATE_LIMIT_MAX_REQUESTS` / `RATE_LIMIT_WINDOW_MS`，健康检查路由在其之前注册故不受限）、用户端登录防暴破（20 次/15 分钟）、后台登录防暴破（5 次/15 分钟，与 `services/adminLoginGuard.js` 的账号锁定叠加）、短信防刷（1 次/60 秒，`SMS_RATE_LIMIT_MAX`）、卡密校验防猜测（10 次/分钟）、上传限流（20 次/分钟）。⚠️ 安全扫描 H-8 起**六个都不按 `NODE_ENV` 豁免**（旧实现有五个挂 `skip: nodeEnv === 'development'`，而 `NODE_ENV` 缺省即 `development`），唯一开关是 `RATE_LIMIT_DISABLED=true`，生产设它后端拒绝启动；计数桶取 `req.ip`，其可信度由 `config/trustProxy.js` 解析的 `TRUST_PROXY` 决定（默认 `loopback`）；响应头统一 `standardHeaders:true`（draft-6）/`legacyHeaders:false`，429 带 `Retry-After` |
